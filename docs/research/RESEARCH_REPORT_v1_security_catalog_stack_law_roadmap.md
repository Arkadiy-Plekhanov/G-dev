# Research Report v1 — Security, Catalog, Stack, Law and Roadmap Strategy

**Дата:** этап между Security Gate (композитные ownership FK) и пивотом на Google-only/Alibaba Cloud/идеалы.
**Статус:** первый из двух раундов исследования в этом проекте. Часть выводов (composite FK, найденные security-каналы, версия PostgreSQL/uuidv7) уже применена и подтверждена вживую в последующей работе (см. `SECURITY_ARCHITECTURE_v1.0.md`). Часть выводов (РФ-хостинг, email+password auth) была явно переопределена более поздним решением владельца о международном продукте на Google-only + Alibaba Cloud (см. `ADR_v2_INTEGRATION.md`) — сохранено здесь как часть трассы решений, а не как актуальная рекомендация.

## TL;DR
- **Внешняя критика по безопасности в основе своей права: composite ownership FK — это правильное, а не избыточное решение**, и его следует принять как основной механизм защиты целостности между арендаторами, оставив same-owner триггер как второй слой (defense in depth). Обход RLS проверками внешних ключей — это подтверждённое, задокументированное поведение PostgreSQL («covert channel»), а не баг вашей схемы.
- **Домен-модель менять не нужно, но каталог качеств стоит вынести в глобальный seed** (из мандалы «Цветок духовных качеств», ~150 качеств онлайн / «более 160» в книге, 12 групп) с персональной таблицей «принятия» — это единственное существенное изменение слоя данных, и текущие 7 качеств мигрируются тривиально.
- **Для русскоязычного продукта с дневниковыми записями хостинг практически обязан быть в РФ** (152-ФЗ, ред. с 01.07.2025): рекомендуется VPS/managed PostgreSQL у российского провайдера (Timeweb Cloud / Selectel), собственный JWT оставить, транзакционные письма — через российский SMTP. *(Переопределено позже: продукт стал международным, РФ-контур отложен — см. ADR v2.)* Готовность проекта — примерно на уровне 55–60%; критический следующий шаг — Security gate.

## Key Findings

1. **FK-проверки в PostgreSQL всегда обходят RLS — это официально задокументировано.** Раздел 5.9 документации PostgreSQL 18 прямо гласит: «Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained. Care must be taken … to avoid "covert channel" leaks». Ваш эмпирический результат — ожидаемое поведение, а не аномалия.
2. **Composite ownership FK — индустриальный best practice, а не паранойя.** Citus/Azure Cosmos DB for PostgreSQL, PlanetScale, ClickHouse, Ecto (Elixir) и множество независимых инженеров рекомендуют именно `(user_id, id)` composite-ключи для арендатор-изоляции на уровне БД. Критик прав.
3. **У composite FK есть реальные издержки**, которые критик недооценил: требуется `UNIQUE(user_id, id)` на всех родительских таблицах, а `ON DELETE SET NULL` ломается на composite-ключах (пытается занулить и `user_id`). Это решается синтаксисом `ON DELETE SET NULL (column)`, добавленным в PostgreSQL 15.
4. **Мандала содержит ~150 качеств онлайн (более 160 в печатной энциклопедии) в 12 цветовых группах** — это оправдывает глобальный курируемый каталог + персональное принятие, по образцу VIA-трекеров и habit-трекеров с встроенными библиотеками.
5. **152-ФЗ (ред. с 01.07.2025) фактически требует первичный сбор ПДн граждан РФ в базах на территории РФ.** Для русскоязычного инди-продукта с чувствительными записями это склоняет чашу к российскому хостингу. *(См. оговорку в статусе выше — продукт стал международным.)*
6. **PostgreSQL 18 (вышел 25.09.2025) даёт нативный `uuidv7()`** — план подтверждён и реализуем «из коробки» (в реализации использован `gen_random_uuid()` как fallback для локальной песочницы на PG16; на целевой инфраструктуре — `uuidv7()`).

## Details

### БЛОК 1. Безопасность multi-tenant PostgreSQL — окончательный вердикт

**1.1. Первоисточник: FK/RI обходят RLS.**
Документация PostgreSQL (раздел «Row Security Policies», в версии 18 — §5.9) содержит дословно: «Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained. Care must be taken when developing schemas and row level policies to avoid "covert channel" leaks of information through such referential integrity checks.» Это же подтверждается в PostgreSQL wiki (страница Row-security), где отдельно описан «FOREIGN KEY side channel»: пользователь может зондировать существование ключей, наблюдая успех/провал DML-операций, и рекомендуется «synthetic keys or no foreign keys at all … between RS tables». В переписке pgsql-hackers (Stephen Frost, 2015) видно, что это сознательное проектное решение с флагом `SECURITY_ROW_LEVEL_DISABLED` в RI-триггерах.

**Вывод:** наблюдаемый факт (пользователь A создал `quality_expression`, ссылающийся на `quality` пользователя B, несмотря на RLS) — это не дыра в конкретной схеме, а фундаментальное свойство движка. RLS в PostgreSQL — «strong access control, but not covert-channel-proof».

**1.2. Сравнение трёх подходов.**

| Критерий | Same-owner триггер (временная затычка) | Composite ownership FK `(user_id, id)` | Комбинация (defense in depth) |
|---|---|---|---|
| Гарантия целостности | Императивная, в коде триггера; надо не забыть на каждой таблице | Декларативная, в схеме; планировщик и движок enforce'ят | Двойная |
| Устойчивость к ошибкам разработчика | Средняя (триггер можно забыть/сломать при рефакторинге) | Высокая (constraint нельзя «забыть») | Наивысшая |
| Производительность | Доп. SELECT в триггере на каждый INSERT/UPDATE | FK-проверка по индексу; `user_id` первым в индексе даёт tenant-locality | — |
| Издержки схемы | Нет доп. колонок | Нужен `user_id` в дочерних таблицах + `UNIQUE(user_id,id)` в родительских | Обе |
| Поведение ON DELETE | Полный контроль в триггере | Требует `ON DELETE SET NULL (col)` (PG15+) для частичного зануления | — |

**Вердикт:** принять composite ownership FK как **основной** механизм, same-owner триггер — только там, где FK физически неприменим (обход циклов произвольной глубины в дереве целей — граф, не прямая ссылка). *(Реализовано: см. `SECURITY_ARCHITECTURE_v1.0.md` — composite FK применены на всех восьми таблицах, старый триггер удалён как избыточный, триггер обхода циклов сохранён.)*

**1.3. Практические следствия composite FK.**
- **UNIQUE(user_id, id) на родительских таблицах обязателен** — SQL-стандарт требует, чтобы FK ссылался на unique-ограничение.
- **ON DELETE.** `ON DELETE SET NULL (col)` — форма с явным списком колонок (PostgreSQL 15, коммит Peter Eisentraut, автор патча Paul Martinez), зануляет только указанную колонку, не весь composite-ключ вместе с `user_id`. Официальная документация: «This is useful for multitenant or sharded schemas, where the tenant or shard ID is included in the primary key of all tables but shouldn't be set to null.»
- **Индексы.** `user_id` первой колонкой — устоявшийся приём (tenant-locality, поддерживает и RLS, и FK, и будущее шардирование).

**1.4. Best practices multi-tenant RLS (2025–2026), сверх composite FK.**
- `SET LOCAL`, не просто `SET`, для session variable — иначе connection pooler «протекает» контекст между запросами.
- Никакого BYPASSRLS/SUPERUSER у прикладной роли.
- **FORCE ROW LEVEL SECURITY** — без него политики не действуют на владельца таблицы. *(Применено.)*
- SECURITY DEFINER-функции — зона риска, минимизировать. *(В проекте не используются нигде.)*
- **VIEW и RLS**: по умолчанию view выполняется с правами создателя, обходя RLS вызывающего — критично для агрегатной статистики. Решение — `security_invoker = true` (PostgreSQL 15+). *(Применено; при проверке ДО фикса обнаружена реальная утечка — пустой тестовый пользователь видел всю статистику и дерево целей владельца через VIEW. После фикса — 0 строк. См. `SECURITY_ARCHITECTURE_v1.0.md`.)*

**1.5. Матрица cross-tenant attack-тестов.**

| # | Атака | Механизм защиты |
|---|---|---|
| 1 | SELECT чужой goal/quality/action/cycle/reflection | RLS |
| 2 | UPDATE чужой строки | RLS |
| 3 | DELETE чужой строки | RLS |
| 4 | expression: свой action + чужой quality | composite FK |
| 5 | expression: чужой action + свой quality | composite FK |
| 6 | parent_id → чужая цель | composite FK |
| 7 | чужая цель/качество в своём цикле | composite FK |
| 8 | reflection → чужой cycle/goal | composite FK |
| 9 | запрос без session-контекста | fail-closed |
| 10 | подделка user_id в INSERT | RLS WITH CHECK |
| 11 | JOIN своей и чужой таблицы | RLS на обеих |
| 12 | чтение через VIEW | security_invoker |
| 13 | FK-зондирование существования | осознанный residual risk |

*(Реализовано как автоматизированный набор из 13 тестов, `backend/tests/test_security_gate.py`, 13/13 зелёных.)*

### БЛОК 2. Каталог качеств из мандалы

**2.1. Структура источника (etikavomne.ru).** «Энциклопедия духовно-нравственных качеств» оформлена как «Цветок духовных качеств»: качества-«лепестки», клик открывает словарную статью. Дословно с вводной страницы: «Все качества в композиции объединены в 12 групп по их внутреннему созвучию и близости, что показано цветом лепестков… Цвет лепестков выбран нами произвольно.» Онлайн-композиция — ~150 качеств; печатное пособие («Энциклопедия духовных качеств в мудрых изречениях и размышлениях», СПб, 2020, сост. Н.В. Башкова) — «более 160».

**Важная оговорка:** полного текстового списка «цвет → качества» сайт не публикует (заложено в интерактивную графику); подтверждена привязка цвета лишь для 5 недавно добавленных лепестков. Полный маппинг потребует ручного разбора композиции или книги. Составители подчёркивают: цвета произвольны, не канон.

**2.2. Структура словарной статьи** (подтверждена на статьях «Мужество», «Стойкость», «Чистота», «Терпимость»): название (+синонимы), краткая характеристика/определение, развёрнутое пояснение (иногда символ), «Близкие понятия», «Взаимодополнительные качества», «Антонимичные понятия», подборка цитат из первоисточников со ссылками, иллюстрации.

**2.3. Рекомендуемая модель данных (глобальный каталог + персональное принятие).**

```
catalog_qualities  -- глобальный seed, без user_id, без RLS
  id, slug, name, name_variants[], color_group, color_name, category,
  short_definition, description, symbol, related_concepts[],
  complementary_qualities[], antonyms[], is_active

user_qualities  -- персональное "принятие"
  id, user_id, catalog_quality_id (FK), focus_of_development,
  development_status, current_level (0-4), adopted_at, review_date
  UNIQUE(user_id, id)  -- цель composite ownership FK из quality_expressions
```

*(Статус реализации на момент этого отчёта: ещё не применено — запланировано отдельным этапом roadmap, "Этап 2: Каталог+идеалы"; финальная версия модели данных — в `ADR_v2_INTEGRATION.md` §2. К моменту сборки ЭТОЙ версии пакета Stage 2 уже реализован и проверен вживую: см. `03_database/05_catalog_ideals_schema.sql`, `06_seed_catalog_and_ideals.py`, `08_migrate_and_cutover.sql`.)*

**2.4. Аналоги.** VIA Classification (Peterson & Seligman, 2004): 24 character strengths под 6 virtue categories, фиксированный глобальный классификатор + персональный профиль поверх него, свободный VIA Survey прошли почти 8 млн человек, 41 язык. Habit-трекеры со встроенными библиотеками (Habitica и др.) устроены аналогично.

### БЛОК 4. Приватность и право (по состоянию первого раунда, для русскоязычной аудитории)

**4.1. 152-ФЗ / локализация.** С 1 июля 2025 действует новая редакция ч. 5 ст. 18 152-ФЗ (ФЗ № 23-ФЗ от 28.02.2025): первичный сбор ПДн граждан РФ — в базах на территории РФ. Штрафы по КоАП (ФЗ № 266-ФЗ) — до 6 млн ₽ первично, до 18 млн ₽ повторно. Трансграничная передача **после** локализации возможна при уведомлении РКН, хотя часть юристов оспаривает эту трактовку — практика не устоялась.

**4.2. Минимум для честного запуска:** privacy policy, уведомление РКН, согласие на обработку ПДн, право на экспорт (JSON) и полное удаление аккаунта (каскад по всем таблицам), основы GDPR при аудитории из ЕС.

**4.3. Шифрование:** HTTPS + disk/DB-level encryption + bcrypt для паролей достаточно на MVP; column-level шифрование отдельных полей — отложить.
