# HANDOFF — состояние проекта и что нужно знать, прежде чем менять код

Документ для того, кто продолжает работу: разработчика или ИИ в IDE. Он не пересказывает
остальные документы, а отвечает на вопросы, которые иначе придётся открывать заново:
**что уже сделано, почему сделано именно так, и чего сознательно НЕ сделано.**

Проверено на состоянии ветки `bugfix/issue-description` — все числа ниже подтверждены
прогоном, не взяты по памяти.

---

## 1. Что это за продукт

Инструмент осознанного развития качеств характера, основанный на традиции Живой Этики
(Агни Йога, наследие Рерихов). Каталог — 169 качеств из «Цветка духовных качеств».

**Ядро, отличающее продукт от habit-трекеров и дневников:** пользователь фиксирует
РЕАЛЬНОЕ ДЕЙСТВИЕ из жизни («провёл сложные переговоры») и отмечает, какие качества в нём
проявились, оценивая каждое отдельно. Одно действие → несколько качеств с разными оценками.
Это не галочка «сделал привычку» и не свободный текст.

## 4. Решения, которые НЕЛЬЗЯ откатить не подумав

Каждое из них уже один раз стоило дорого. Прежде чем менять — прочитай почему.

### 4.1 Безопасность: RLS, а не проверки в коде

Изоляция данных между пользователями держится на Row-Level Security в самой БД, а не на
`WHERE user_id = ...` в запросах. `get_conn(user_id)` выставляет сессионную переменную,
которую читают политики RLS. **Любой запрос в обход `get_conn` — дыра в безопасности.**
На это есть 13 атакующих тестов (`test_security_gate.py`), они не декоративные.

Подробно: `docs/specifications/03_SECURITY_ARCHITECTURE_v1.0.md`.

### 4.2 Шкала роста: 1–4 именованные ступени, 0 — ВНЕ шкалы

- **1 Spark** (emerging) → **2 Kindling** (developing) → **3 Flame** (established) → **4 Gem** (embodied)
- **0 = «пошло в другую сторону»** — это НЕ низшая ступень, а запись другого рода.

`0` исключается из всех средних (`quality_stats` считает среднее только по 1–4), а срывы
считаются отдельными полями (`inversion_count`). Причина: если срыв стоит на одной числовой
шкале с ростом, среднее молча смешивает два разных вопроса — «насколько развито качество»
и «как часто я срываюсь», и оба ответа становятся нечестными.

Миграция 10. Тест-инвариант: при оценках 4, 2, 0 среднее должно быть **3.0, а не 2.0**.

### 4.3 Стадия вычисляется, вручную не задаётся

`growthStage()` (`frontend/src/lib/growthStage.js`) выводит ступень из среднего балла.
Ручные поля `current_level` и `dev_status_code` **удалены** миграцией 16: интерфейса для
них так и не появилось, у всех навсегда оставались значения по умолчанию.

**Порога «минимум N проявлений» намеренно нет.** Он был, и его убрали: у свежего аккаунта
почти все качества имеют 1–2 проявления, и «not enough data yet» вставало на каждой строке
каждого экрана — захламляло восприятие именно в момент знакомства с продуктом.

### 4.4 Каталог общий, личное — только фокус

«Принятое качество» как понятие для пользователя **не существует**. Каталог из 169 у всех
одинаковый; личное состояние ровно одно — в фокусе качество или нет. Строка
`user_qualities` создаётся молча при добавлении в фокус.

Следствия, которые легко случайно сломать:
- `/qualities/:id` принимает **и** id принятого качества, **и** `catalog_quality_id` — для
  человека это одна и та же «карточка качества».
- `QualityLibrary` — ОДИН компонент для страницы Qualities и для шага онбординга. Раньше
  это были две почти одинаковые реализации, и они разошлись: онбординг работал, страница
  качеств показывала только фокусные.

### 4.5 Оценка качества необязательна

На экранах действия и рефлексии фокус-качества показаны сразу строками с рейтингом.
Неоценённое качество просто не отправляется на бэкенд. Требовать оценку каждого — значит
заставлять человека оценивать то, что в этом поступке не проявлялось.

### 4.6 Рефлексия с качествами создаёт действие

`POST /reflections` с непустым `qualities` атомарно создаёт И рефлексию, И действие с
проявлениями качеств (одна транзакция). Без качеств действие не создаётся, `action_id`
остаётся `NULL` — это нормальное состояние, а не «недозаполненная» рефлексия.

Причина: `quality_expressions.action_id` — `NOT NULL`, и вся аналитика (тренды,
`quality_stats`, сравнение «выше/ниже обычного») держится на нём. Второй параллельный
источник качеств расщепил бы её.

### 4.7 Ответы API типизированы -- кроме одного, намеренно

38 из 46 операций имеют `response_model` (остальные 7 -- `DELETE` со статусом 204).
Единственное исключение -- `GET /v1/me/export`: схема ФИЛЬТРУЕТ поля, а выгрузка по
GDPR обязана включать всё, включая колонки, добавленные позже. Это решение, а не
недоделка; отмечено и в коде.

Подключение схем сразу поймало реальный баг: `CycleOut` не объявлял `goals` и
`qualities`, и FastAPI начал молча их отфильтровывать -- экран сезона остался бы без
списков, без единой ошибки в логах.

### 4.8 Спокойный дизайн — это позиция, не недоделка

Нет обнуляемых серий (streaks), очков, наказывающей геймификации. Это осознанный выбор,
подкреплённый исследованием: серии дают краткосрочное удержание ценой тревоги и
бросания после срыва. Продукт про осознанность, а не про залипание.

Подробно: `docs/MASTER_PLAN.md`, `docs/research/HARD_ROAD_FEATURE_MAP.md`.

## 5. Ловушки, на которых уже спотыкались

**Схема и код едут раздельно.** Миграции накатываются вручную (`reset-neon.sh`), бэкенд
Render деплоит сам при мёрдже в `main`. **Порядок: сначала миграции, потом мёрдж.**
Наоборот — продакшен падает на первом же запросе. Это уже случалось:
`column qs.inversion_count does not exist`.

**Список миграций живёт в ОДНОМ месте** — `scripts/apply-migrations.sh`. Makefile, CI и
`reset-neon.sh` используют его. Раньше список был продублирован в трёх местах, и добавление
миграции обновило только одно — та самая авария выше.

**Тесты идут против живого бэкенда.** Нужен поднятый API и БД. Падение с
`Connection refused` почти всегда значит «забыл поднять», а не «сломал код».

**Асинхронность в тестах.** Первый запрос к элементу после загрузки — только `findBy*`,
не `getBy*`. И если проверок несколько — весь блок в `waitFor`, иначе тест зелёный на
быстрой машине и красный на медленной.

**Прокрутка сбрасывается вручную.** `components/ScrollToTop.jsx` возвращает окно в начало
при каждом переходе. Без него SPA сохраняет позицию от предыдущего экрана -- неправильно
ВЕЗДЕ, просто на iOS Safari выглядит как «пустой фон, пока не тронешь». Прокручивается
ОКНО, не `.screen` (у него нет ограниченной высоты). Встроенный `ScrollRestoration` из
React Router здесь не подходит: он работает только с data-роутером.

**`100vh` включает адресную строку** -- и в iOS Safari, и в Android Chrome. Везде, где
нужна высота экрана, идёт пара `100vh` (запасной) + `100dvh` (рабочий).

**Правки под конкретный движок -- только в одном месте:** блок «СЛОЙ ПЛАТФОРМЕННОЙ
НОРМАЛИЗАЦИИ» в начале `global.css`. Ветвления по браузеру в проекте нет и не должно
появиться -- почему, и что считать правкой под среду, а что обычной ошибкой:
`docs/ENVIRONMENTS.md`.

**`RatingControl` — это `radiogroup`.** Кнопки имеют `role="radio"`, не `"button"`;
`getByRole('button')` их не найдёт.

## 6. Чего сознательно НЕ сделали

- **Мобильная проверка на 360px** — верстка сделана без жёстких пиксельных ширин, но
  вживую в браузере на узком экране не измерялась.
- **Переименование Actions → Acts** — обсуждалось, отложено владельцем.
- **Отдельные карточки контекстов** — проверено по исходной спецификации: аналитика по
  контексту задумывалась ВНУТРИ карточки качества, она там и есть.
- **Русская локализация** — каркас i18n готов, каталог хранит русские названия, но
  интерфейс пока только английский.
- **Фазы 2–5** (implementation intentions, мобильное приложение, десктоп, монетизация) —
  расписаны в `docs/MASTER_PLAN.md`, не начаты.
