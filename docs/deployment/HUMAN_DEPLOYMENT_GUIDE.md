# Руководство по развёртыванию — для владельца проекта

Это твоя версия документа для Qwen (`QWEN_DEPLOYMENT_SPEC.md` в этой же папке, тот же порядок этапов) —
но написанная так, чтобы ты мог провести весь путь сам, руками, понимая, что и зачем
делаешь на каждом шаге, вообще без ИИ. Оба документа описывают ОДНУ и ту же
последовательность — можешь в любой момент переключиться между «делаю сам» и «прошу ИИ
сделать это» посередине пути.

**Принцип, который держит всю эту последовательность:** ни рубля/доллара не тратится,
пока весь пайплайн (миграции → бэкенд → фронтенд → CI/CD → HTTPS) не проверен целиком
хотя бы один раз на бесплатной инфраструктуре. Только после этого имеет смысл платить за
Alibaba Cloud.

## Этап 0 — Git-репозиторий (сделано, но важно понимать зачем)

Весь код до сих пор передавался файлами вне системы контроля версий — это был главный
риск на этом этапе (случайно потерять версию, не видеть историю изменений, не иметь
единой точки правды). Теперь есть настоящий `git`-репозиторий со структурой:

```
backend/    frontend/    database/    docs/    docker-compose.yml    Makefile
```

**Что сделать тебе:** завести аккаунт на github.com (если ещё нет), создать **приватный**
репозиторий, затем из корня этого проекта:
```bash
git remote add origin git@github.com:<твой-аккаунт>/<имя-репозитория>.git
git push -u origin main
```
Приватный репозиторий на бесплатном тарифе GitHub — без ограничения по числу приватных
репозиториев, с 2000 минут GitHub Actions/месяц и полноценным GitHub Issues+Projects
(канбан-доска) — этого достаточно для одного разработчика с ИИ-ассистентами в качестве
исполнителей. Заводить отдельно Jira не нужно: у неё те же возможности по факту, но
отдельный логин, отдельный API, и жёсткий лимит в 100 запусков автоматизации в месяц —
никакого выигрыша для твоего случая, только лишняя система.

## Этап 1 — Локальная разработка на твоём компьютере (Docker Compose)

**Зачем этот этап:** до сих пор вся работа шла в одноразовой облачной песочнице, которая
не сохраняет состояние между сессиями. Теперь у тебя есть возможность продолжать
разработку на своей машине, с сохранением истории через git.

**Что нужно установить:** Docker Desktop (бесплатно для личного использования и малого
бизнеса до $10M выручки — твой случай подходит) **или** Podman Desktop (полностью
бесплатная альтернатива при любом масштабе, если хочешь не думать о лицензионных
условиях вообще — команды идентичны, `docker compose` → `podman compose`).

**Запуск:**
```bash
cp .env.example .env
# впиши реальный GOOGLE_CLIENT_ID и VITE_GOOGLE_CLIENT_ID если он уже есть у тебя;
# для локальной разработки можно оставить плейсхолдер -- реальный Google-вход
# всё равно нельзя протестировать без настоящего client id.

make dev-up
```

**Важная деталь, которую стоит понимать, а не просто выполнять:** `make dev-up` запускает
Postgres, ЖДЁТ, пока он реально поднимется, и только ПОТОМ применяет все 15 файлов миграций
по порядку — и только после этого стартует бэкенд. Если бы всё запускалось одновременно
(`docker compose up` без разбора), бэкенд попытался бы подключиться к базе ролью
`app_writer`, которой ещё физически не существует (она создаётся только первой миграцией)
— и просто падал бы в цикле перезапуска. Это не баг Docker, это порядок причины и
следствия: нельзя подключиться под ролью, которая ещё не создана.

**Проверка:** `make dev-test` — должно показать **69 тестов бэкенда + 23 теста
фронтенда**, все зелёные. Это тот же самый набор тестов, что гонялся всё это время в
облачной песочнице — теперь он гоняется у тебя локально, доказывая, что переход на
Docker ничего не сломал.

**Переход к этапу 2, когда:** `docker compose up` поднимает весь стек с нуля без ручного
вмешательства (кроме `.env`), и `make dev-test` полностью зелёный.

## Этап 2 — Бесплатный удалённый стейджинг (Neon + Render + Cloudflare) — ✅ ЗАВЕРШЁН И ПОДТВЕРЖДЁН ЖИВЬЁМ

**Это не план — это факт, проверенный руками 27.08.2026.** Настоящий Google-вход через настоящий
задеплоенный фронтенд, через настоящий задеплоенный бэкенд, в настоящую базу Neon — пройден от
начала до конца: вход → онбординг → залогировать действие → увидеть статистику. Ниже — точная
запись того, как это было сделано, включая реальные провалы по пути и что их вызвало (это не
гипотетические предостережения — каждое реально случилось хотя бы раз в процессе).

**Готово в репозитории:** `render.yaml` (Ohio, Python-рантайм, `PYTHON_VERSION` зафиксирован),
`frontend/wrangler.jsonc` (Cloudflare — см. ниже, почему это не «классический» Pages),
`scripts/reset-neon.sh` (полный чистый пересев Neon одной командой, с проверкой результата).

### 1. Neon

Создай проект (Postgres 18 — это дефолт Neon сейчас; `uuidv7()` в PG18 — настоящая функция ядра,
но схема пока использует `gen_random_uuid()` и переписывать её для этого не нужно). Neon называет
базу по умолчанию `neondb`, а у нас везде захардкожено `selfdev` — создай отдельную базу в том же
проекте:
```sql
CREATE DATABASE selfdev;
```

**Neon Auth (тумблер при создании проекта) — НЕ включай.** Это не проверка токена, а замена
всего потока входа: Google редиректил бы на инфраструктуру Neon, не на наш бэкенд, а сессии жили
бы в схеме `neon_auth`, привязанной к конкретному Neon-проекту — переезд на Alibaba в Tier 3
сломал бы вход. У нас уже есть своя рабочая, протестированная система.

**Миграции — через `scripts/reset-neon.sh`, не вручную по шагам.** Этот скрипт появился не для
удобства, а потому что ручной прогон один раз реально сломался незаметно: все SQL-миграции прошли
успешно, а один Python-шаг (`06_seed_catalog_and_ideals.py`) тихо упал где-то посреди борьбы с DNS — и это обнаружилось не сразу, только явной
проверкой `count(*)`. Скрипт делает DROP/CREATE базы, все 15 шагов, и сам сверяет числа в конце
(ожидает 169 качеств в каталоге и 3 идеала), падая с ошибкой, если что-то не сошлось — молчаливый частичный провал больше не пройдёт незамеченным:
```bash
export NEON_ADMIN_URL="postgresql://neondb_owner:<пароль>@<host>-pooler.<region>.aws.neon.tech/selfdev?sslmode=require&channel_binding=require"
bash scripts/reset-neon.sh
```
Запускай **не через `docker compose exec postgres`** — именно эта связка (локальный контейнер
Postgres, Docker Desktop, WSL2) не резолвила внешний хост Neon вообще (`Temporary failure in
name resolution`) — задокументированное поведение WSL2/Docker Desktop, не проблема Neon и не
что-то, специфичное для этого проекта. `psql`/`python3` напрямую с хоста WSL — стабильно работали
на всём протяжении. Роль `app_writer` не удаляется дропом базы (роли — на уровне проекта, не
базы), так что после пересева `DATABASE_URL` в Render трогать не нужно.

**Порядок выкладки важен и не подлежит перестановке.** Схема и код едут раздельно: миграции --
твоя ручная команда с хоста, бэкенд Render деплоит сам при мёрдже в `main`. Поэтому:

```
1. reset-neon.sh   -- Neon получает новую схему
2. мёрдж в main    -- Render деплоит бэкенд, Cloudflare -- фронтенд
```

Если поменять шаги местами, новый бэкенд встретит старую схему и упадёт на первом же запросе
(именно так однажды и случилось: `column qs.inversion_count does not exist` -- бэкенд уже читал
колонки миграции 10, которой в базе ещё не было). Между шагами продакшен фактически лежит,
поэтому промежуток стоит держать коротким.

### 2. Render — бэкенд

⚠️ **`render.yaml` читается ТОЛЬКО если сервис создаётся через Dashboard → New → Blueprint.**
Ручное «New Web Service» с заполнением формы полностью игнорирует файл — это и было настоящей
причиной первой неудачи, не содержимое самого YAML.

`render.yaml` уже фиксирует `PYTHON_VERSION=3.12.9` — у Render дефолт для новых сервисов
плавающий (сейчас это 3.14.3), а весь проект тестировался на 3.12.

После первого деплоя впиши в Render → Environment три значения (`sync: false` в `render.yaml` —
значит «спроси меня», не хранить в git):
- `DATABASE_URL` — **pooled**-строка Neon (`-pooler` в хосте), роль `app_writer` (не
  `neondb_owner`), база `/selfdev` (не `/neondb`)
- `GOOGLE_CLIENT_ID` — реальный Client ID
- `CORS_ORIGINS` — JSON-массив строкой, например `["https://<адрес-с-cloudflare>"]` (подтверждено
  вживую, что `pydantic-settings` так и парсит) — реальный адрес появится только на шаге 3, пока
  можно оставить заглушку `["http://localhost:5173"]`

`JWT_SECRET` Render сгенерирует сам. Регион — Ohio (совпадает с тем, где оказался Neon; латентность
важнее совпадения с будущим Alibaba-регионом на этом этапе).

### 3. Cloudflare — фронтенд. Это НЕ классический «Cloudflare Pages»

Важно понимать заранее, не как сюрприз после провала: в 2026 году интерфейс Cloudflare по
умолчанию предлагает новую, единую модель **Workers + Static Assets** (`npx wrangler deploy`), а
не старый интерфейс Pages с полями «Framework preset» / «Build output directory». Это реальное,
текущее отличие продукта, не устаревшее предположение.

Нужен `frontend/wrangler.jsonc` (уже в репозитории):
```jsonc
{
  "name": "<должно совпадать с именем проекта в Cloudflare, иначе Wrangler переопределит с предупреждением>",
  "compatibility_date": "<сегодняшняя дата на момент реального деплоя>",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}
```
`not_found_handling: "single-page-application"` — это весь нужный фикс SPA-роутинга целиком,
официально задокументированная настройка именно для этой модели.

**Не создавай `frontend/public/_redirects`.** Такой файл был создан раньше (под старое
предположение о классическом Pages) и реально сломал деплой: новая валидация Cloudflare отвергает
правило `/* /index.html 200` с ошибкой «Invalid _redirects configuration... Infinite loop
detected» (код 100324). Если увидишь именно эту ошибку — файл нужно удалить целиком, не
редактировать: `wrangler.jsonc` уже полностью закрывает эту задачу, и два механизма конфликтуют.

В форме подключения репозитория: **Path** — смени на `frontend` (в документации Cloudflare это
поле дословно не описано под этим именем, но на практике вело себя ровно как обычный «root
directory» — сборка реально шла из `frontend/` и корректно находила и `wrangler.jsonc`, и `dist/`).
**Build command** — обязательно впиши явно, с переменными прямо внутри команды:
```
VITE_API_BASE_URL=<реальный URL Render>/v1 VITE_GOOGLE_CLIENT_ID=<реальный client id> npm run build
```
Это не костыль: отдельные поля «Variable name/Variable value» в этой форме — переменные
**рантайма воркера** (`env.VAR` в серверном коде), а не то, что попадает в сборку Vite — реальное,
задокументированное различие именно этой модели, легко упустить. Ни одно из двух значений не
секретное (Client ID изначально публичный, адрес бэкенда тоже не секрет), так что вписать их прямо
в команду — правильное решение, не временный обход. **Deploy command** — оставь `npx wrangler deploy`.

### 4. Обратный шаг — CORS

Когда появится реальный адрес Cloudflare — вернись в Render и замени заглушку `CORS_ORIGINS` на
настоящий. Это обязательный шаг, не мелочь: без него браузер блокирует запросы к бэкенду ещё до
того, как они уйдут с фронтенд-домена.

### 5. Google OAuth origin

console.cloud.google.com → APIs & Services → Credentials → тот же Client ID → Authorized
JavaScript origins → добавь реальный адрес Cloudflare. `localhost:5173` не убирай — добавляем
новый origin, не заменяем. Изменение иногда применяется не мгновенно — если сразу после
сохранения ошибка повторится, подожди немного, прежде чем искать другую причину.

**Переход к этапу 3, когда захочешь** — этап 2 уже полностью пройден и подтверждён; следующий шаг
не заблокирован ничем техническим, только решением, когда его начинать.

## Этап 3 — Alibaba Cloud, пробный период, точная копия продакшена

**Зачем этот этап:** этап 2 доказал, что пайплайн работает. Этап 3 доказывает, что он
работает именно на ТОЙ инфраструктуре, за которую ты в итоге будешь платить — но пока
бесплатно, на триале.

**⚠️ Самое важное на этом этапе, требует твоего личного внимания, не делегируй ИИ без
понимания:** пробный период ApsaraDB RDS for PostgreSQL устроен НЕ так, как пробный период
ECS. ECS-инстанс на подписке просто истекает без всяких списаний. **RDS — это
pay-as-you-go, и по истечении триала (30 дней на обычном аккаунте, 60 — на корпоративном)
он автоматически переходит на платный тариф и начинает списывать деньги с привязанной
карты — без дополнительного предупреждения.** Поставь себе напоминание в календаре на
день окончания триала: либо вручную удалить пробный RDS-инстанс, либо осознанно
превратить его в продакшен (тогда это уже не сюрприз, а решение).

**Регистрация:** аккаунт Alibaba Cloud International, номер телефона (не материковый
Китай), способ оплаты. Паспорт/удостоверение личности НЕ требуется для обычной работы в
регионе Singapore — только если будешь подписывать контракты или разворачиваться в
материковом Китае.

**Что создать (регион — обязательно Singapore/ap-southeast-1):**
1. **ECS**: `ecs.t6-c1m2.large` или `ecs.e-c1m2.large` (2 vCPU/4 ГБ), Ubuntu 24.04 LTS.
   Группа безопасности: только порты 22 (SSH), 80, 443. SSH-ключ, не пароль.
2. **ApsaraDB RDS for PostgreSQL**: выбери **версию 16 или 17** в селекторе консоли (обе
   безопасны и полностью поддерживаются). Версия 18 технически доступна, и в ней можно
   проверить, появилась ли нативная функция `uuidv7()` — но это отдельный эксперимент,
   не обязательный для этого этапа; текущий код и так работает через собственную
   генерацию UUID на стороне приложения, и менять это не обязательно. Внеси во whitelist
   внутренний (не публичный) IP ECS-инстанса.
3. На ECS: Python 3.12, nginx, systemd-юнит для бэкенда (gunicorn с uvicorn-воркерами,
   слушает только 127.0.0.1:8000 — наружу смотрит только nginx), Let's Encrypt/Certbot
   для HTTPS (не платный SSL-сервис Alibaba — Let's Encrypt бесплатен и автопродлевается).
4. **OSS + CDN**: бакет в Singapore, включить статический хостинг/SPA-режим, залить
   фронтенд через `ossutil sync` (не через community GitHub Action — у него есть известный
   баг, сбрасывающий правила бакета при каждом деплое), подключить CDN с HTTPS.
5. Расширить GitHub Actions ещё одним workflow — деплой на Alibaba (SSH для бэкенда,
   `ossutil sync` для фронтенда).
6. Подключить Sentry (бесплатный тариф Developer: 5000 ошибок/мес, этого достаточно) и
   бесплатный UptimeRobot-монитор на `/health`-эндпоинт.
7. **Провести одну учебную проверку восстановления из бэкапа**: в консоли RDS —
   «Backup and Restoration» → восстановить во ВРЕМЕННЫЙ новый инстанс → проверить, что
   данные на месте → удалить временный инстанс. Это не страховка «на всякий случай» — это
   единственный способ реально знать, что бэкапы вообще восстанавливаются, а не просто
   существуют.

**Переход к этапу 4, когда:** тот же пайплайн работает на настоящей инфраструктуре
Alibaba; HTTPS настоящий (не самоподписанный); проверка восстановления из бэкапа реально
проведена; ты осознанно решил, что делать с триал-инстансом RDS до его истечения.

## Этап 4 — Платный продакшен

Только после того, как этап 3 полностью пройден. Переведи (или пересоздай) RDS-инстанс на
**High-availability Edition** — это единственный способ получить SLA 99.99% и, что важнее,
возможность point-in-time recovery (у Basic Edition её физически нет — это не про
надёжность соединения, это про то, есть ли у тебя вообще возможность восстановиться на
конкретный момент времени). Направь DNS домена на реальную инфраструктуру. Прогони весь
чек-лист приёмки с этапа 3 ещё раз, уже против продакшена, прежде чем объявлять его живым.

**Ориентир по деньгам на этом этапе:** managed HA PostgreSQL — самая крупная статья
расходов, по грубой оценке порядка $85–120/мес; burstable ECS — $30–65/мес (может быть
бесплатным весь первый год за счёт триала ECS, если успеть перейти на подписку до
истечения); OSS+CDN — по трафику, обычно небольшая сумма при старте. Итого реалистичный
старт — **порядка $40–90/мес**, не разово, а именно как ежемесячная стоимость.

## Итоговая последовательность одной строкой

Локально на своей машине (бесплатно) → Neon+Render+Cloudflare Pages (бесплатно) → Alibaba
Cloud на триале, точная копия продакшена (бесплатно, но с картой на файле и напоминанием
про RDS) → Alibaba Cloud платный продакшен. Деньги тратятся только на последнем шаге, и
только после того, как всё остальное уже доказанно работает.
