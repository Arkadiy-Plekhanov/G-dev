# Руководство по развёртыванию — для владельца проекта

Это твоя версия документа для Qwen (`QWEN_DEPLOYMENT_SPEC.md`, тот же порядок этапов) —
но написанная так, чтобы ты мог провести весь путь сам, руками, понимая, что и зачем
делаешь на каждом шаге, вообще без ИИ. Оба документа описывают ОДНУ и ту же
последовательность — можешь в любой момент переключиться между «делаю сам» и «прошу ИИ
сделать это» посередине пути.

**Принцип, который держит всю эту последовательность:** ни рубля/доллара не тратится,
пока весь пайплайн (миграции → бэкенд → фронтенд → CI/CD → HTTPS) не проверен целиком
хотя бы один раз на бесплатной инфраструктуре. Только после этого имеет смысл платить за
Alibaba Cloud.

---

## Этап 0 — Git-репозиторий (сделано, но важно понимать зачем)

Весь код до сих пор передавался файлами вне системы контроля версий — это был главный
риск на этом этапе (случайно потерять версию, не видеть историю изменений, не иметь
единой точки правды). Теперь есть настоящий `git`-репозиторий со структурой:

```
backend/    frontend/    database/    docs/    docker-compose.yml    Makefile
```

**Что сделать тебе:** завести аккаунт на github.com (если ещё нет), создать **приватный**
репозиторий, затем из корня этого проекта:
```bash
git remote add origin git@github.com:<твой-аккаунт>/<имя-репозитория>.git
git push -u origin main
```
Приватный репозиторий на бесплатном тарифе GitHub — без ограничения по числу приватных
репозиториев, с 2000 минут GitHub Actions/месяц и полноценным GitHub Issues+Projects
(канбан-доска) — этого достаточно для одного разработчика с ИИ-ассистентами в качестве
исполнителей. Заводить отдельно Jira не нужно: у неё те же возможности по факту, но
отдельный логин, отдельный API, и жёсткий лимит в 100 запусков автоматизации в месяц —
никакого выигрыша для твоего случая, только лишняя система.

## Этап 1 — Локальная разработка на твоём компьютере (Docker Compose)

**Зачем этот этап:** до сих пор вся работа шла в одноразовой облачной песочнице, которая
не сохраняет состояние между сессиями. Теперь у тебя есть возможность продолжать
разработку на своей машине, с сохранением истории через git.

**Что нужно установить:** Docker Desktop (бесплатно для личного использования и малого
бизнеса до $10M выручки — твой случай подходит) **или** Podman Desktop (полностью
бесплатная альтернатива при любом масштабе, если хочешь не думать о лицензионных
условиях вообще — команды идентичны, `docker compose` → `podman compose`).

**Запуск:**
```bash
cp .env.example .env
# впиши реальный GOOGLE_CLIENT_ID и VITE_GOOGLE_CLIENT_ID если он уже есть у тебя;
# для локальной разработки можно оставить плейсхолдер -- реальный Google-вход
# всё равно нельзя протестировать без настоящего client id.

make dev-up
```

**Важная деталь, которую стоит понимать, а не просто выполнять:** `make dev-up` запускает
Postgres, ЖДЁТ, пока он реально поднимется, и только ПОТОМ применяет все 9 файлов миграций
по порядку — и только после этого стартует бэкенд. Если бы всё запускалось одновременно
(`docker compose up` без разбора), бэкенд попытался бы подключиться к базе ролью
`app_writer`, которой ещё физически не существует (она создаётся только первой миграцией)
— и просто падал бы в цикле перезапуска. Это не баг Docker, это порядок причины и
следствия: нельзя подключиться под ролью, которая ещё не создана.

**Проверка:** `make dev-test` — должно показать **53 теста бэкенда + 12 тестов
фронтенда**, все зелёные. Это тот же самый набор тестов, что гонялся всё это время в
облачной песочнице — теперь он гоняется у тебя локально, доказывая, что переход на
Docker ничего не сломал.

**Переход к этапу 2, когда:** `docker compose up` поднимает весь стек с нуля без ручного
вмешательства (кроме `.env`), и `make dev-test` полностью зелёный.

## Этап 2 — Бесплатный удалённый стейджинг (Neon + Render + Cloudflare Pages)

**Готово в репозитории:** `render.yaml` (Render сам прочитает настройки — build/start команды, регион Singapore, health-check — без ручного тыканья в дашборд) и `frontend/public/_redirects` (без него прямые ссылки на `/goals/123` будут давать 404 — SPA-роутинг живёт в браузере, не на сервере).

**1. Neon** — создай проект (Postgres 18, регион любой близкий; Neon Auth **не включай** — см. ниже почему), скопируй connection string. Примени миграции 01→06,08,09 тем же способом, что и локально, только указав `-d "$NEON_CONNECTION_STRING"` вместо локальной БД. **Смени пароль `app_writer`** с дефолтного `change_me_in_production` перед тем, как это станет доступно из интернета:
```bash
psql "$NEON_CONNECTION_STRING" -c "ALTER ROLE app_writer WITH PASSWORD '<новый-пароль>'"
```

**Про Neon Auth (тумблер при создании проекта) — сознательно НЕ включать.** Это не проверка токена, а замена всего потока входа: Google должен был бы редиректить на инфраструктуру Neon, а не на наш бэкенд, и сессии/JWT жили бы в схеме `neon_auth`, привязанной к конкретному Neon-проекту — то есть переезд на Alibaba в Tier 3 сломал бы аутентификацию. У нас уже есть своя рабочая, протестированная, руками подтверждённая система (Google Identity Services + свой JWT) — сохраняем её на всех уровнях без изменений.

**2. Render** — подключи GitHub-репозиторий, Render найдёт `render.yaml` сам и предложит создать сервис `qualities-api-staging` (Singapore, бесплатный тариф, автодеплой на каждый push). После первого деплоя впиши в Render dashboard (Environment): `DATABASE_URL` (из Neon), `GOOGLE_CLIENT_ID`, и `CORS_ORIGINS` (заполнишь после шага 3, когда будет URL Cloudflare Pages) — `JWT_SECRET` Render сгенерирует сам. Бесплатный веб-сервис засыпает после 15 минут без запросов — первый запрос после сна ждёт около минуты, это нормально для стейджинга.

**3. Cloudflare Pages** — подключи тот же репозиторий, укажи: root directory `frontend`, build command `npm run build`, output directory `dist`. После первого деплоя получишь URL вида `https://<project>.pages.dev` — впиши его в Render как `CORS_ORIGINS=["https://<project>.pages.dev"]` (шаг 2), и в Cloudflare Pages env vars впиши `VITE_API_BASE_URL` = URL твоего Render-сервиса + `/v1`.

**Переход к этапу 3, когда:** `git push` в `main` автоматически деплоит и бэкенд (Render), и фронтенд (Cloudflare Pages) без ручных действий; живой Cloudflare-URL реально разговаривает с живым Render-URL; полный цикл (Google-вход → онбординг → действие → статистика) проходит на этом стейджинге.

## Этап 3 — Alibaba Cloud, пробный период, точная копия продакшена

**Зачем этот этап:** этап 2 доказал, что пайплайн работает. Этап 3 доказывает, что он
работает именно на ТОЙ инфраструктуре, за которую ты в итоге будешь платить — но пока
бесплатно, на триале.

**⚠️ Самое важное на этом этапе, требует твоего личного внимания, не делегируй ИИ без
понимания:** пробный период ApsaraDB RDS for PostgreSQL устроен НЕ так, как пробный период
ECS. ECS-инстанс на подписке просто истекает без всяких списаний. **RDS — это
pay-as-you-go, и по истечении триала (30 дней на обычном аккаунте, 60 — на корпоративном)
он автоматически переходит на платный тариф и начинает списывать деньги с привязанной
карты — без дополнительного предупреждения.** Поставь себе напоминание в календаре на
день окончания триала: либо вручную удалить пробный RDS-инстанс, либо осознанно
превратить его в продакшен (тогда это уже не сюрприз, а решение).

**Регистрация:** аккаунт Alibaba Cloud International, номер телефона (не материковый
Китай), способ оплаты. Паспорт/удостоверение личности НЕ требуется для обычной работы в
регионе Singapore — только если будешь подписывать контракты или разворачиваться в
материковом Китае.

**Что создать (регион — обязательно Singapore/ap-southeast-1):**
1. **ECS**: `ecs.t6-c1m2.large` или `ecs.e-c1m2.large` (2 vCPU/4 ГБ), Ubuntu 24.04 LTS.
   Группа безопасности: только порты 22 (SSH), 80, 443. SSH-ключ, не пароль.
2. **ApsaraDB RDS for PostgreSQL**: выбери **версию 16 или 17** в селекторе консоли (обе
   безопасны и полностью поддерживаются). Версия 18 технически доступна, и в ней можно
   проверить, появилась ли нативная функция `uuidv7()` — но это отдельный эксперимент,
   не обязательный для этого этапа; текущий код и так работает через собственную
   генерацию UUID на стороне приложения, и менять это не обязательно. Внеси во whitelist
   внутренний (не публичный) IP ECS-инстанса.
3. На ECS: Python 3.12, nginx, systemd-юнит для бэкенда (gunicorn с uvicorn-воркерами,
   слушает только 127.0.0.1:8000 — наружу смотрит только nginx), Let's Encrypt/Certbot
   для HTTPS (не платный SSL-сервис Alibaba — Let's Encrypt бесплатен и автопродлевается).
4. **OSS + CDN**: бакет в Singapore, включить статический хостинг/SPA-режим, залить
   фронтенд через `ossutil sync` (не через community GitHub Action — у него есть известный
   баг, сбрасывающий правила бакета при каждом деплое), подключить CDN с HTTPS.
5. Расширить GitHub Actions ещё одним workflow — деплой на Alibaba (SSH для бэкенда,
   `ossutil sync` для фронтенда).
6. Подключить Sentry (бесплатный тариф Developer: 5000 ошибок/мес, этого достаточно) и
   бесплатный UptimeRobot-монитор на `/health`-эндпоинт.
7. **Провести одну учебную проверку восстановления из бэкапа**: в консоли RDS —
   «Backup and Restoration» → восстановить во ВРЕМЕННЫЙ новый инстанс → проверить, что
   данные на месте → удалить временный инстанс. Это не страховка «на всякий случай» — это
   единственный способ реально знать, что бэкапы вообще восстанавливаются, а не просто
   существуют.

**Переход к этапу 4, когда:** тот же пайплайн работает на настоящей инфраструктуре
Alibaba; HTTPS настоящий (не самоподписанный); проверка восстановления из бэкапа реально
проведена; ты осознанно решил, что делать с триал-инстансом RDS до его истечения.

## Этап 4 — Платный продакшен

Только после того, как этап 3 полностью пройден. Переведи (или пересоздай) RDS-инстанс на
**High-availability Edition** — это единственный способ получить SLA 99.99% и, что важнее,
возможность point-in-time recovery (у Basic Edition её физически нет — это не про
надёжность соединения, это про то, есть ли у тебя вообще возможность восстановиться на
конкретный момент времени). Направь DNS домена на реальную инфраструктуру. Прогони весь
чек-лист приёмки с этапа 3 ещё раз, уже против продакшена, прежде чем объявлять его живым.

**Ориентир по деньгам на этом этапе:** managed HA PostgreSQL — самая крупная статья
расходов, по грубой оценке порядка $85–120/мес; burstable ECS — $30–65/мес (может быть
бесплатным весь первый год за счёт триала ECS, если успеть перейти на подписку до
истечения); OSS+CDN — по трафику, обычно небольшая сумма при старте. Итого реалистичный
старт — **порядка $40–90/мес**, не разово, а именно как ежемесячная стоимость.

## Итоговая последовательность одной строкой

Локально на своей машине (бесплатно) → Neon+Render+Cloudflare Pages (бесплатно) → Alibaba
Cloud на триале, точная копия продакшена (бесплатно, но с картой на файле и напоминанием
про RDS) → Alibaba Cloud платный продакшен. Деньги тратятся только на последнем шаге, и
только после того, как всё остальное уже доказанно работает.
