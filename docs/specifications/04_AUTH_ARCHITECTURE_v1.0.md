# Auth Architecture v1.0 — этап 1 (Google-only) закрыт

**Статус:** реализовано, применено к живой БД, 20/20 тестов зелёных (7 auth + 13 security gate, вместе — без конфликтов). Полный сквозной прогон через реальный FastAPI ASGI-стек: Google-вход → CRUD → статистика — под новым префиксом `/v1`.

## Identity model
`users.google_sub` — единственный стабильный идентификатор (не email: он «может меняться, не является ключом» — ADR v2 §4). `email` намеренно освобождён от UNIQUE (был им в старой email+password-модели, это больше не верно). `password_hash` остался в схеме, но nullable — зарезервирован под будущие методы входа, в MVP всегда NULL. БД сама требует хоть какой-то способ входа: `CHECK (google_sub IS NOT NULL OR password_hash IS NOT NULL)`.

## Поток входа
Клиент получает Google ID token (любая платформа — веб/мобильные используют один и тот же нативный Google Sign-In) → `POST /v1/auth/google {id_token}` → бэкенд верифицирует через официальную `google-auth` (`verify_oauth2_token`: подпись по JWKS, `aud`, `exp` — библиотека делает это сама; вручную сверяется `iss`) → find-or-create по `google_sub`, при повторном входе синхронизирует имя/аватар из свежих claims → выдаёт пару токенов: access JWT (30 мин) + refresh (60 дней, случайный, в БД хранится только SHA-256 хэш).

## Refresh-ротация с обнаружением повторного использования
Каждый `POST /v1/auth/refresh` **обязан** заменить токен новым: старый помечается `revoked_at`, новый — со свежим сроком. Если предъявлен уже отозванный токен — это сигнал кражи (легитимный клиент так поступить не может, он всегда работает с последним выданным), и в ответ отзываются **все** активные refresh-токены пользователя, а не только предъявленный. Поймана и исправлена настоящая гонка: наивная реализация коммитила это массовое отозвание внутри той же транзакции, что и последующий `raise HTTPException` — а `get_conn()` откатывает транзакцию при любом исключении, включая намеренные отказы, так что отзыв никогда не сохранялся. Тест `test_reused_old_refresh_token_revokes_whole_session` поймал это по факту (легитимный токен, выданный на шаге ротации прямо перед атакой, продолжал работать), не по теории — исправлено явным `commit()` перед `raise` именно в этой ветке.

## Что покрыто тестами (`tests/test_auth_google.py`, 7/7)
Первый вход создаёт пользователя; повторный вход тем же `google_sub` возвращает того же пользователя (не дублирует); недействительный токен отклоняется; защищённый роут без токена отклоняется; ротация делает старый refresh нерабочим; **replay уже использованного refresh-токена отзывает всю сессию целиком** (включая честно выданный новый); logout отзывает конкретный токен.

**Честная граница тестирования:** сама криптографическая проверка подписи Google (JWKS) не может быть прогнана вживую из песочницы — нет сетевого доступа к серверам Google (это архитектурное ограничение среды разработки, не проекта) и нет реального Google OAuth client id. Подменена через `app.dependency_overrides` **только эта одна точка** (`get_google_verifier`) — вся остальная цепочка (find-or-create, RLS-контекст, JWT, ротация) отработана по-настоящему, включая реальный Postgres. Библиотека `google-auth`, которая делает саму верификацию, — официальная, документированная Google как рекомендуемая для продакшена; входящий в неё код тестируется самой Google, не нуждается в повторном тестировании с нашей стороны.

## Побочные находки и исправления по пути
1. Забытый `GRANT` на новую таблицу `refresh_tokens` для `app_writer` — поймано первым же прогоном теста (`permission denied`), не постфактум в проде.
2. Гонка commit/rollback в reuse-detection (см. выше) — поймано вторым прогоном.
3. `users.email` был `UNIQUE` по старой модели — снят, соответствие ADR v2 восстановлено.

## Что осознанно не входит в этот этап
Email/password — удалены как путь регистрации (кнопка на будущее, колонка в схеме осталась). 2FA, другие соцсети — не сейчас. Привязка Telegram-бота отдельным link-кодом — отдельная, ещё не реализованная часть (архитектура описана в ADR v2 §4, код — в этап после каталога/фронтенда). Идемпотентность записи действий — вопреки более ранней черновой формулировке роадмапа, отнесена туда, где ей место по смыслу — к этапу 3 (полный API), а не к auth.
