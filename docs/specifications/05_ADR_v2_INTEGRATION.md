# Architecture Decision Record v2 — интеграция решений владельца

**Статус:** все девять решений приняты как константы. Ядро (домен, security-архитектура: RLS + composite ownership FK + FORCE RLS + security_invoker + 13 attack-тестов) не пересматривается — оно достраивается. Скриншоты — концепт; этот документ — спецификация, и она главнее.

---

## 1. Решения и их архитектурные следствия

| № | Решение | Следствие |
|---|---|---|
| 1 | Учёт любых качеств свободен; фокус — отдельная композиция, 3 пути онбординга | Новые сущности `ideals`, `ideal_qualities`; фокус остаётся полем `user_qualities.focus_code` — три пути сходятся в один результат |
| 2 | Спецификация важнее эскизов | Исправлена семантика нуля в Add Action (см. §3.4) |
| 3 | Мультиплатформа с единым аккаунтом | Один FastAPI `/v1` как единственный носитель логики; все клиенты — тонкие (§5) |
| 4 | Международный продукт, хостинг без ограничений | РФ-контур исключён из scope; en — основной язык, ru — второй (§6) |
| 5 | Кастомных качеств нет | `user_qualities.catalog_quality_id` становится `NOT NULL`; путь `custom_name` удаляется из модели |
| 6 | Каталог насыщается к релизу | Рабочий сид: ~15–20 качеств + ~6 идеалов; полный каталог (~150 + переводы) — отдельный этап перед публикацией |
| 7 | Только Google-вход, автосоздание аккаунта | `users` перестраивается под OAuth-only (§4); email/password — не в MVP, схема готова к добавлению позже |
| 8 | Alibaba Cloud как единая основа | Целевой контур §7; факты (версии PG, тарифы) требуют проверки на актуальность |
| 9 | Каждый этап — завершённый продукт | Roadmap пересобран (§8) |

## 2. Доменная дельта: идеалы и композиция фокуса

```
ideals                                -- глобальный курируемый каталог, БЕЗ RLS (reference)
  id uuid PK
  slug text UNIQUE                    -- 'marcus-aurelius'
  category text                       -- spiritual | historical | philosophers | leaders
  portrait_asset text
  name jsonb                          -- {"en": "...", "ru": "..."}  (§6)
  summary jsonb
  is_active bool

ideal_qualities                       -- композиция идеала, упорядоченная
  ideal_id uuid REFERENCES ideals(id) ON DELETE CASCADE
  catalog_quality_id uuid REFERENCES catalog_qualities(id)
  rank smallint NOT NULL              -- 1 = самое характерное
  PRIMARY KEY (ideal_id, catalog_quality_id)
```

**Механика трёх путей (все — операции над `user_qualities`):**
- **Идеал:** пользователь выбирает идеала и размер фокуса N (напр. 7/15/25, но N — свойство выбора, не константа схемы). Система принимает top-N качеств идеала по `rank` c `focus_code='current_focus'`. Идеал — **генератор композиции, не постоянная связь**: у пользователя сохраняется только `users.chosen_ideal_id` (nullable, UX-метка «мой идеал»); дальнейшие правки фокуса идеала не касаются.
- **Тест:** модель закладывается сейчас (`assessment_questions`, варианты с весами качеств, `assessment_sessions`, скоринг → рекомендованная композиция), реализация — этапом после MVP; в онбординге путь виден как «скоро». Результат теста — тот же вызов «принять композицию».
- **Ручной выбор:** прямые операции add/remove focus над `user_qualities`.
- Редактирование композиции после любого пути — одинаковое и свободное.

Деликатность каталога идеалов (религиозные фигуры) — решается фильтром категорий и нейтральной, уважительной подачей текстов; в контент-гайд каталога.

## 3. Инварианты записи действия (исправление эскиза)

3.1. Качество попадает в запись действия **только явным выбором** («проявилось в этом действии»).
3.2. Шкала 0–4 появляется **после** выбора качества; дефолта «0 всем фокус-качествам» не существует.
3.3. Невыбранное качество ⇒ записи `quality_expression` нет вообще (не ноль!).
3.4. **0 = «качество было релевантно, но проявлено противоположным образом / провал»** — это осмысленная отрицательная оценка, не отсутствие. Схема уже enforce'ит это CHECK-инвариантом; UI обязан ему соответствовать, иначе статистика отравляется ложными нулями.
3.5. Фокус-качества в форме показываются первыми (подсказка), но доступен весь принятый набор и поиск по каталогу.

## 4. Auth: Google-only

```
users
  id uuid PK DEFAULT uuidv7()
  google_sub text UNIQUE NOT NULL     -- стабильный идентификатор Google (НЕ email)
  email citext NOT NULL               -- из профиля Google; может меняться, не является ключом
  display_name text NOT NULL
  avatar_url text
  locale text NOT NULL DEFAULT 'en'
  timezone text NOT NULL DEFAULT 'UTC'
  chosen_ideal_id uuid REFERENCES ideals(id)
  password_hash text NULL             -- зарезервировано под будущие методы, в MVP всегда NULL
  created_at / updated_at timestamptz
```

Поток: клиент получает Google ID token → `POST /v1/auth/google` → бэкенд верифицирует (iss/aud/exp, подпись по JWKS) → find-or-create по `google_sub` → выдаёт **наш** access JWT (короткий TTL) + refresh-токен с ротацией (для мобильных долгоживущих сессий). Mobile-клиенты используют нативный Google Sign-In и тот же эндпоинт. Telegram-бот: привязка одноразовым link-кодом (в вебе «Привязать Telegram» → код → бот `/link CODE` → chat_id связывается с user_id). Риск Google-only (потеря Google-аккаунта = потеря входа) принят осознанно; страховка — схема заранее допускает добавление второго метода без миграции.

## 5. Единый API для всех платформ

Один FastAPI как единственный носитель бизнес-логики; версия `/v1`; OpenAPI — контракт для веба, приложений и ботов. Закладывается сразу (чтобы мобильные клиенты и боты не потребовали ломать API): refresh-токены; курсорная пагинация; идемпотентность создания действия (`client_request_id UNIQUE(user_id, client_request_id)` — против даблтапов и офлайн-повторов); `occurred_at` — дата в календаре пользователя, `users.timezone` — источник интерпретации; никакой бизнес-логики в клиентах.

## 6. i18n с нуля

Коды (`slug`, `code`) — англоязычные, стабильные, никогда не локализуются. Отображаемые тексты каталогов (`catalog_qualities`, `ideals`, будущие `assessment_questions`) — **JSONB `{locale: text}`** на MVP (атомарно, просто, без JOIN'ов; вынос в таблицу переводов — только если появится реальная потребность в переводческом workflow). UI — react-i18next, `en` основной, `ru` второй, ICU-формат. Русскоязычный первоисточник каталога переводится на английский на этапе насыщения (этап 6), не раньше.

## 7. Целевой контур Alibaba Cloud (международный)

ECS (или Serverless App Engine — сравнить по цене/простоте) для FastAPI в Docker; **ApsaraDB RDS for PostgreSQL** с автобэкапами/PITR; OSS + CDN для статики веб-PWA; KMS/Secrets Manager для секретов; CloudMonitor + сторонний Sentry и внешний uptime-чекер; регион — Сингапур или Франкфурт по аудитории; CI — GitHub Actions → деплой в Alibaba Cloud. **Честная оговорка:** доступные мажорные версии PostgreSQL (есть ли 17/18) и актуальные тарифы нужно проверить перед фиксацией; если PG18/`uuidv7()` недоступен — uuid v7 генерируется приложением (готовые библиотеки), схема не меняется. Trade-off'ы Alibaba против мейнстрима (документация, комьюнити) принимаются осознанно, решение владельца зафиксировано.

## 8. Roadmap v2 (каждый этап — завершённый продукт)

| Этап | Содержание | Acceptance | Не делаем |
|---|---|---|---|
| 0. Security gate | Composite FK, FORCE RLS, security_invoker, 13 attack-тестов в CI | Все тесты зелёные; Security doc v1.0 | Новые фичи |
| 1. Auth-ядро | Google-only, users v2, наш JWT+refresh, идемпотентность | Вход с чистого Google-аккаунта создаёт пользователя; refresh-ротация покрыта тестами | Email/password, 2FA, соцсети кроме Google |
| 2. Каталог+идеалы | catalog_qualities (NOT NULL связь), ideals+ideal_qualities, рабочий сид ~15–20 качеств / ~6 идеалов, пути «идеал»+«ручной» | Онбординг обоими путями формирует фокус; ремап 7 качеств владельца | Тест-путь (заглушка «скоро»), полный каталог, кастомные качества |
| 3. API v1 | Полный контракт, экспорт JSON, полное удаление аккаунта, pytest | Цикл вход→композиция→действие→оценки→статистика→экспорт→удаление зелёный в тестах | Admin-панель |
| 4. Веб-PWA (en) | Онбординг 3 путей, ежедневная практика (семантика §3), цели, качества, статистика | Полный ежедневный цикл на телефоне; PWA устанавливается | Графическая «красота» сверх системы, геймификация, соцфичи |
| 5. Деплой+бета | Alibaba Cloud контур, HTTPS, бэкап+проверенный restore, Sentry, staging, privacy policy | Restore успешен; 3–10 бета-пользователей неделю без инцидентов | Автоскейлинг, multi-region |
| 6. Насыщение | Полный каталог ~150 качеств + идеалы, en+ru переводы, ru-локаль UI | Контент вычитан; переключение локали корректно | Другие языки сверх en/ru |
| 7. Публикация | Открытая регистрация, финальный attack-suite и restore на проде, лендинг | Внешний пользователь проходит полный цикл | Всё, что не влияет на честный запуск |

После публикации (уже спроектировано, реализуется потом): тест-путь онбординга; мобильные приложения (решение по обёртке — на этапе выбора, кандидаты Capacitor поверх той же PWA vs React Native); Telegram-бот; циклы и рефлексия в UI; РФ-контур при потребности.

**Переоценка готовности с учётом новых требований:** схема ~85% (дельта: users v2, ideals, NOT NULL связь каталога), security ~40% (гейт не пройден), auth ~20% (переделка на Google-only), API ~45%, frontend 0%, deploy ~5%, контент каталога ~10%. Интегрально ~45–50% — ниже прошлой оценки не из-за регресса, а из-за честного расширения scope (идеалы, i18n, мультиплатформенные основы).
