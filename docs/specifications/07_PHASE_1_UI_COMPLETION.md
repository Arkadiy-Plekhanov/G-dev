# Спецификация Фазы 1 — «Завершить построенное»

> Часть дорожной карты `docs/MASTER_PLAN.md`. Эта фаза **не меняет API** — весь backend уже
> написан, покрыт тестами и работает на Render. Задача фазы: сделать доступной пользователю
> функциональность, которая уже оплачена разработкой.
>
> Принцип приёмки фазы: **ни один готовый эндпоинт не остаётся без экрана.**

| Эндпоинт | Состояние API | Экран |

## 1. Циклы развития

**Что это в доменной модели.** Цикл — период (start_date … end_date) с набором целей и качеств
в фокусе, статусом и итоговым резюме. Ограничение БД: **один активный цикл на пользователя**
(при попытке создать второй API возвращает код `ONE_ACTIVE_CYCLE_ALREADY_EXISTS`).

### 1.1 Экран списка циклов — `/cycles`

Хронологический список: активный цикл первым и визуально выделен, ниже — завершённые.
На карточке: название, период, статус, число привязанных целей и качеств.

Пустое состояние — не «нет данных», а объяснение смысла:
> «Цикл — это отрезок времени, на который вы берёте несколько качеств в работу. Он даёт
> ответ на вопрос "стало ли лучше за этот период" — то, чего не даёт отдельное действие.»

### 1.2 Создание/редактирование цикла — `/cycles/new`, `/cycles/:id/edit`

Поля: название, даты начала и конца, статус (из `/v1/reference/options/cycle_status`),
описание, множественный выбор целей и качеств.

**Обязательно обработать:** попытку создать второй активный цикл. Ошибка приходит машиночитаемым
кодом — показать понятный текст и предложить открыть текущий активный цикл, а не показывать
сырую ошибку.

**Важная деталь API:** `PATCH /v1/cycles/{id}` **полностью заменяет** наборы `goal_ids` и
`quality_ids`. Форма редактирования должна присылать полный список, а не дельту.

### 1.3 Карточка цикла — `/cycles/:id`

Заголовок с периодом и прогрессом по времени (сколько дней прошло из общего срока).
Привязанные цели и качества с текущей статистикой каждого. Действия, совершённые внутри периода
цикла. Рефлексии, привязанные к циклу. Поле резюме — заполняется при завершении.

## 2. Рефлексии

**Что это в доменной модели.** Структурированная запись с типом (`daily` / `weekly` / по циклу),
привязкой к цели или циклу и семью содержательными полями: что сработало, что не сработало,
какие качества замечены, инсайт, что изменить, что застряло, что изменить в следующем цикле.

**Почему структура, а не свободный текст:** исследования показывают, что структурированная
рефлексия эффективнее свободного дневника. Все семь полей уже есть в API.

### 2.1 Список рефлексий — `/reflections`

Обратный хронологический список. На карточке: дата, тип, первая строка инсайта, метки привязки
(к какой цели или циклу).

### 2.2 Создание рефлексии — `/reflections/new`

**Не показывать все семь полей сразу** — это стена текста, которую никто не заполнит.
Показывать по типу:

| Тип | Поля |
|---|---|
| Ежедневная | Что сработало · Что не сработало · Инсайт |
| Еженедельная | + Какие качества замечены · Что изменить |
| По циклу | Все семь, включая «что застряло» и «что изменить в следующем цикле» |

Все поля необязательны — сохранить можно, заполнив хотя бы одно. Плейсхолдеры формулируются
как вопросы, а не как названия колонок БД («Что именно сработало?», а не «what_worked»).

### 2.3 Точки входа

Кнопка на карточке цикла (рефлексия по циклу), на карточке цели (рефлексия по цели), на главной
(ежедневная). Тип и привязка проставляются автоматически по точке входа — пользователь не должен
выбирать это вручную.

## 3. История действий — `/actions`

Лента всех действий с курсорной пагинацией (API отдаёт `before_occurred_at` + `before_created_at`).
Загрузка следующей страницы по прокрутке или кнопкой «показать ещё» — но **не** бесконечная лента
без конца: это дарк-паттерн вовлечения, противоречащий принципам продукта.

На карточке действия: название, дата, цель, контекст, проявленные качества с их оценками
(цветовое кодирование: 0 — отдельным, тревожным цветом, 1–4 — нарастающей насыщенностью,
как уже сделано в `RatingControl`).

Группировка по дням с заголовками-датами.

## 4. Визуализация статистики

**Самая содержательная часть фазы.** Backend уже считает всё нужное — на фронте это показано
числами, что обесценивает работу.

### 4.1 Карточка качества — `/qualities/:id`

Сейчас: `avg_score_all_time`, `avg_score_30d`, `trend`, `stability`, `confidence` текстом.

Должно быть:
- **Спарклайн динамики** по проявлениям во времени + текущее среднее крупно
- **Тренд** — стрелка с направлением и подписью, а не слово
- **Уверенность** — честный индикатор: при малом числе проявлений прямо писать
  «данных пока мало — нужно ещё N проявлений», а не показывать среднее по двум точкам как факт
- **Разбивка по контексту** — горизонтальные полосы: в каких контекстах качество проявляется
  чаще и сильнее (данные уже приходят из API)
- **Последние проявления** — список с оценками и комментариями

### 4.2 Карточка цели — `/goals/:id`

Ключевое, что уже считает backend и что не показано: **сравнение проявления качества в рамках
этой цели против обычного уровня качества** (порог ±0.3 → `above_usual` / `as_usual` / `below_usual`).

Это самая содержательная метрика продукта — она отвечает на вопрос «эта цель вытягивает из меня
лучшее или худшее?». Показать явно и заметно, а не как строку в таблице.

### 4.3 Главная — `/`

Текущий фокус качеств с мини-динамикой каждого. Одно предложение-вывод вместо списка цифр
(в Фазе 1 — простейшее правило по имеющимся данным; полноценные рекомендации — Фаза 2).

---

## 5. Data-quality-alerts

Мягкие, не блокирующие подсказки о пробелах: действия без указанной цели, качества без пересмотра
давно и т.п. (эндпоинт уже отдаёт `check_name`, `record_id`, `label`).

**Тон критичен.** Это не «ошибки» и не «вы делаете неправильно» — это «здесь можно уточнить».
Показывать в профиле или отдельной секцией, **не** на главной: главная не должна встречать
пользователя списком его недоработок.

## 6. Мобильная полировка

Сейчас интерфейс работает, но собран как каркас. Требования фазы:

- **Цели касания** — минимум 44×44pt, ничего мельче
- **Логирование действия — минимум тапов.** Это ежедневный сценарий, критичный к трению
  (эталон в категории — Daylio, два тапа). Оценка качеств должна ставиться на одном экране
  сегментами, а не многошаговым визардом
- **Безопасные зоны** — учёт выреза и домашней полосы iPhone
- **Никакого горизонтального скролла** ни на одном экране на 360px ширины
- **Состояния загрузки и ошибок** на каждом экране — не белый экран
- **Тёмная тема** — базовое требование категории (есть у всех изученных конкурентов)
- **Уважение `prefers-reduced-motion`** — уже заложено в `global.css`

Дизайн-направление остаётся прежним — «полевой дневник натуралиста», как зафиксировано
в `frontend/src/styles/global.css`: бумажный фон, тёмно-зелёные чернила, Fraunces/IBM Plex.

## 7. Порядок работы

Подэтапы делаются последовательно, каждый доводится до зелёных тестов и проверяется руками,
прежде чем начинается следующий:

1. История действий (простейшее, разминает работу с пагинацией)
2. Циклы (список → создание → карточка)
3. Рефлексии (список → создание → точки входа)
4. Визуализация статистики
5. Data-quality-alerts
6. Сквозная мобильная полировка

## 8. Критерии приёмки фазы

- [ ] Ни один готовый эндпоинт API не остаётся без экрана
- [ ] Полный путь проходится на телефоне: онбординг → действие → цикл → рефлексия → статистика
- [ ] Все существующие тесты зелёные (55 backend + 12 frontend), новые экраны покрыты тестами
      в том же стиле — против живого бэкенда, не моков
- [ ] Ошибка «второй активный цикл» показывается понятным текстом, а не сырым кодом
- [ ] На 360px ширины нет горизонтального скролла ни на одном экране
- [ ] Ручная проверка владельцем на реальном устройстве пройдена
- [ ] `npm run build` чистый, размер бандла не вырос радикально (сейчас ~310 КБ JS)
