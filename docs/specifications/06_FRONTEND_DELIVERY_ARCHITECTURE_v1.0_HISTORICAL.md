# Frontend/Delivery Architecture: готовые UI-платформы vs свой интерфейс

**Вопрос:** можно ли вместо своего UI использовать готовые инструменты (Metabase/Retool и похожие) для веба, телефона и ботов поверх уже готовой Postgres-схемы.
**Метод:** цены и возможности всех трёх ключевых кандидатов проверены поиском (не по памяти — рынок no-code/BI быстро меняется), а модель доступа к БД — реально создана и протестирована на той же живой Postgres-песочнице, что и в прошлом документе.

**Вывод одним абзацем:** Да, но не один инструмент на всё. У задачи три разных режима использования (быстрый ежедневный ввод, аналитика, редкий админ), и это structurally разные UI-задачи — один инструмент, который одинаково хорош во всех трёх, не существует. Разумная архитектура — гибридная: **Metabase** (self-hosted, бесплатно) — под три отчёта «Аналитики»; **AppSheet, теперь указанный на Postgres вместо Google Sheets** — под ежедневную практику на телефоне, потому что под него уже проделан огромный объём точного дизайна (лист «Настройки AppSheet»); Telegram-бот — в любом случае свой код, тут выбора нет ни у кого.

---

## 1. Матрица потребностей

| | Ежедневная практика (действие + качества, быстро, часто) | Аналитика (3 отчёта) | Админ/справочники (редко) |
|---|---|---|---|
| **Веб** | AppSheet как установленный PWA, либо позже — свой лёгкий фронт | Metabase (self-hosted) | AppSheet или Retool (free tier) |
| **Телефон** | AppSheet — нативное iOS/Android приложение | Metabase адаптивно открывается в браузере | почти не нужен |
| **Бот (Telegram)** | Свой код — короткий диалоговый флоу `/log` | Свой код — `/stats` текстом или ссылка на дашборд Metabase | — |

Это не три отдельных вкуса — это три разных технических требования: быстрый ввод нужен *низкая задержка на смартфоне + офлайн*, аналитика нужна *drill-down по графикам*, админка нужна *generic-таблица с фильтрами*. Профессиональный инструмент под каждый режим — не компромисс, а более здравое решение, чем один универсальный.

---

## 2. Кандидаты — проверено, не по памяти

### Metabase
Open source (self-host, бесплатно, AGPL) + платные Cloud-тарифы (Starter $100/мес, Pro $575/мес). Read/BI-инструмент по своей природе: подключается к Postgres, строит графики/дашборды без кода, умеет drill-down. **Запись данных не его профиль** — «writable connections» существуют только как платный add-on поверх Starter/Pro, а не базовая возможность. Для наших трёх read-model'ов (`quality_stats`, `goal_hierarchy`, `action_stats` — те самые VIEW, что уже проверены в прошлом документе) — это прямое попадание: Metabase увидит их как обычные таблицы и сразу сможет строить графики без единой строчки кода с нашей стороны.

Для одного пользователя self-hosted Open Source покрывает всё нужное с запасом — платные тарифы актуальны только при множестве пользователей/встраивании в чужой продукт, что не наш случай.

### Retool
Low-code конструктор *внутренних инструментов* (админки, CRUD, полевые операции), не BI и не consumer-приложение. Есть Retool Mobile — реально нативные iOS/Android-приложения (React Native рантайм), с камерой/сканером/геолокацией/биометрией, офлайн-режимом и push-уведомлениями. Бесплатный тариф — до 5 пользователей, для одного человека этого достаточно; офлайн-режим требует уже Business-тарифа (от €46/строитель/мес).

Ключевое ограничение для нашего случая: Retool Mobile спроектирован и маркетируется под *«полевые команды»* — сканирование склада, инспекции, учёт — не под личный рефлексивный дневник. UI ощущается как рабочий инструмент, а не как приложение, в которое хочется возвращаться каждый день по собственному желанию. Плюс собственный движок Retool Mobile, по независимым отзывам, тормозит при 50+ компонентах на экране — для карточки цели с несколькими блоками статистики это реалистичный сценарий.

### AppSheet, указанный на Postgres — а не на Google Sheets
Вот здесь — главная находка этого разбора. **AppSheet официально и нативно поддерживает подключение к внешней PostgreSQL-базе** (My Account → Sources → New Data Source → Cloud Database → Postgres), при условии что база доступна из интернета (Cloud SQL, RDS, любой облачный хостинг с открытым портом и IP-доступом для серверов AppSheet). Для AppSheet ваши `goals`/`actions`/`quality_expressions` и наши VIEW — просто ещё один источник таблиц, точно как раньше был Google Sheets.

Почему это важно именно для этого проекта: лист **«Настройки AppSheet»** внутри уже проаудированного Excel-файла — это, по сути, готовая спецификация AppSheet-приложения: типы полей, Ref-связи, Valid_If-инварианты (которые почти дословно совпадают с CHECK-констрейнтами, которые мы уже написали и проверили), VC-альтернативы статистики, список того, что скрыть, чек-лист P0. Указать AppSheet на новую Postgres-схему вместо Google Sheets — это не «начать заново», а **реализовать уже готовый, детально продуманный дизайн** на более прочном фундаменте.

Минусы, честно: подключение к облачной базе данных доступно только на тарифе **Enterprise Plus — $20/пользователь/месяц** (Starter за $5 и Core за $10 умеют только Google Sheets/Excel/файловое хранилище, без облачных БД — это легко упустить при поверхностном сравнении цен). Ваша Postgres-база должна быть доступна из интернета для серверов AppSheet — реальное расширение поверхности атаки по сравнению с полностью закрытой базой. И UI, при всей мобильности, остаётся «во вкусе AppSheet» — не полностью бespoke.

### Коротко про остальных
**Appsmith, Budibase** — открытые аналоги Retool, self-hosted и бесплатные, тот же профиль применения (внутренние CRUD-инструменты), тот же UX-разрыв с личным дневником. **NocoDB** — открытый Airtable-подобный слой поверх существующей Postgres-базы (не создаёт свою, может смотреть на нашу) — разумная бесплатная альтернатива Retool именно для админки/справочников, если хочется остаться полностью self-hosted и не платить даже за AppSheet.

## 3. Архитектура доступа к БД — создано и проверено вживую

Ни один из этих инструментов не должен иметь ни владельческих прав на схему, ни, тем более, суперпользователя. Два разных уровня доступа, каждый протестирован реальным подключением по TCP с паролем:

```sql
-- Metabase: только чтение, включая будущие таблицы
CREATE ROLE metabase_reader LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE selfdev TO metabase_reader;
GRANT USAGE ON SCHEMA public TO metabase_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO metabase_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO metabase_reader;

-- AppSheet / бот: чтение+запись доменных данных, без DDL
CREATE ROLE app_writer LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE selfdev TO app_writer;
GRANT USAGE ON SCHEMA public TO app_writer;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_writer;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_writer;
```

**Проверено:** под `metabase_reader` `SELECT` из `quality_stats` отработал и вернул реальную строку (`avg_score_all_time=2.33`, `trend=Растёт` — те же тестовые данные из прошлого документа), `INSERT` в `goals` упал с `permission denied for table goals`, `DROP TABLE goals` упал с `must be owner of table goals`. Под `app_writer` `INSERT` в `development_cycles` прошёл и вернул новый `id`, `DROP TABLE goals` так же упал с `must be owner`. Именно так и должно быть: Metabase физически не может испортить данные, AppSheet/бот физически не может тронуть схему.

Если admin-панель тоже строится в AppSheet — использует ту же роль `app_writer`. Если для админки взять Retool/NocoDB отдельно — им нужна ровно та же роль `app_writer`, отдельно заводить не обязательно.

## 4. Сетевая архитектура — реальный компромисс

Это стоит проговорить прямо, раз дневник содержит личную рефлексию, а не только метрики. Two paths:

- **Всё self-hosted** (Postgres + self-hosted Metabase на одном небольшом VPS/частной сети) — база вообще не обязана быть доступна из интернета публично, только узкий, аудируемый слой (для бота/будущего API). Самый закрытый вариант.
- **AppSheet как SaaS** требует, чтобы Postgres принимал входящие соединения от серверов AppSheet — то есть база обязана быть доступна извне (с IP-allowlist на диапазоны AppSheet и обязательным SSL). Это реальное, а не гипотетическое расширение поверхности атаки в обмен на скорость и готовый мобильный UI.

Компромисс не устраняется — он или принимается осознанно (что и предлагаю, с SSL + IP-allowlist + отдельной непривилегированной ролью `app_writer`, как выше), или AppSheet исключается из архитектуры в пользу полностью закрытого self-hosted стека (Metabase + NocoDB/Retool self-hosted + свой бот), ценой отказа от уже готового AppSheet-дизайна и от нативного мобильного приложения.

## 5. Бот — в любом случае свой код

Ни один из этих инструментов не говорит с Telegram напрямую в формате настоящего диалога. Бот (aiogram на Python или grammY на Node) подключается к Postgres той же ролью `app_writer` и реализует короткий разговорный флоу: «какое действие?» → «какие качества?» → «оценка 0–4 по каждому» → подтверждение — то есть именно ту многошаговую логику, которую нельзя выразить одной generic-таблицей ни в одном из готовых конструкторов. Для простых команд (`/stats`, «что сегодня») бот может либо сам сделать `SELECT` из `quality_stats`/`goal_hierarchy`, либо просто прислать ссылку на публичный дашборд Metabase — выбирать не обязательно сейчас.

## 7. Открытый вопрос — уже не мне решать

Единственное место, где я не берусь дать однозначный «профессиональный» ответ — это ежедневная практика: AppSheet-on-Postgres против полностью кастомного PWA. Мой личный крен — начать с AppSheet: огромный объём уже готового, точного дизайна («Настройки AppSheet») не пропадает зря, подключение официально поддерживается, и это буквально тот путь, который изначально планировался для проекта, просто на более прочном фундаменте. Риск минимален: данные полностью портативны, и если через месяц ежедневного использования AppSheet-версия будет ощущаться «как рабочий инструмент, а не как личный дневник» — это будет понятно на реальном опыте, а не на бумаге, и переезд на кастомный PWA не потребует ни одной миграции данных, только новый фронт поверх той же схемы и тех же ролей.

Но это вопрос вкуса и того, насколько для тебя лично важна полировка интерфейса инструмента, которым будешь пользоваться каждый день — а это решать не мне.
