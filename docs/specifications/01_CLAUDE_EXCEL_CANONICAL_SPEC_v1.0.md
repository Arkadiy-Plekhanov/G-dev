## 0. Как читать этот документ

- Формулы приводятся **дословно**, как они хранятся в `.xlsx` (включая `_xlfn.` — обязательный префикс, которым Excel/LibreOffice кодирует функции, появившиеся после 2007 г.: `MAXIFS`, `MINIFS`). Это не опечатка и не мусор — так формат `.xlsx` физически хранит имя функции в XML.
- Все формулы даны для **строки 2** (первая строка данных) каждого листа. Filled-down копии для строк 3…N идентичны с точностью до сдвига номера строки — это проверено программно построчной нормализацией, см. п. 0.1.
- «Флаг: …» — везде булева формула, возвращающая текстовое `"Да"` или пустую строку `""` (не `TRUE/FALSE`). Живой смысл: колонка либо пуста, либо содержит буквально слово «Да».
- «служ.: …» — скрытые вспомогательные колонки, физически хранящие промежуточные вычисления только для нужд листа «Аналитика». Лист «Настройки AppSheet» (C29–C33) прямо говорит: при переносе на AppSheet эти колонки нужно скрыть/удалить — их роль берут на себя `Related`/`SELECT()`. В SQL это тоже не постоянные поля, а вычисляемые в момент запроса.
- Реальный объём данных на момент аудита — крошечный (первые тестовые записи, даты — середина августа 2026, то есть буквально «на этой неделе» по внутреннему времени книги). Это не прототип с фейковыми данными — это реальный старт эксплуатации.

### 0.1. Методологическая оговорка: «2 разных паттерна формулы» — это не баг

Автоматическая проверка консистентности (нормализация номера строки в каждой формуле) первоначально помечала почти каждую формульную колонку как «2 разных паттерна». Проверено вручную на нескольких колонках (`Цели!D`, `Цели!M` и др.) — причина техническая, не смысловая: диапазоны в формулах вида `$A$2:$B$201` **начинаются именно со строки 2**, а строка 2 — это и есть первая строка данных. Поэтому у строки 2 (и только у неё) собственный относительный номер строки численно совпадает с константной нижней границей диапазона, и наивная нормализация путает одно с другим.

**Вывод: формулы во всех проверенных колонках заполнены вниз строго идентично, без ручных правок и разрывов.** Это важный положительный результат аудита сам по себе — заявленная «Behavioral Equivalence» опирается на то, что поведение одинаково для любой строки, а не только для примеров.

## 1. Философия и инварианты верхнего уровня (по листу «Инструкция»)

1. **Цепочка:** Цель → Действие → Качество → Оценка. Качества — не дочерние элементы целей, а «сеть поверх дерева»: одно качество проявляется во многих целях через действия.
2. **Явный запрет:** система **намеренно не считает общий балл/индекс личности**. Это не упущение, а осознанное архитектурное решение, дважды подтверждённое независимо — и в самой книге (Инструкция, п.1), и в Layer 3 (`Анализ_Airtable...pdf`, раздел 2: «Система не должна выдавать общий балл личности»).
3. **«Текущий уровень» (Качества!I) — РУЧНОЕ поле.** Это отдельный, специально задокументированный разворот прежнего поведения: в более ранней версии оно автоматически показывало последнюю оценку; было решено, что единичная оценка может быть случайной, а «текущий уровень» — это собственное устойчивое суждение человека, отдельное от статистики. Статистика (L–S) существует **рядом**, а не **вместо** этого суждения.
4. Цвета-легенда (Инструкция, п.8): светло-жёлтая заливка = строки-примеры (можно менять/удалять свободно); светло-красная = сработавший флаг качества данных; колонки «служ.: …» — не трогать руками.
5. Явно закреплена одна намеренная демонстрационная аномалия: `Действие Д-0004` **сознательно** оставлено без цели — «живой пример строки Качество данных» (Инструкция, п.8). Это подтверждается и фактическим состоянием данных (раздел 3.3 ниже).

### 4.3 Настройки AppSheet — целевая спецификация переноса (4 раздела)

Этот лист — не просто заметки, а формальная спецификация типов/ключей/правил для AppSheet, дополненная точными формулами-эквивалентами для переноса статистики в Virtual Columns.

**Раздел A (P0, обязательно):** таблица «Таблица | Столбец | Тип AppSheet | Key | Ref → | Valid_If | Комментарий» для каждого ключевого поля. Из неё явно следуют бизнес-правила, которые в самом Excel реализованы только как **реактивные флаги**, а не блокировки:
- `Цели.ID родителя`: `Valid_If: OR(ISBLANK([_THIS]), [_THIS]<>[ID])` — прямая самоссылка **блокируется на вводе**; более длинные циклы A→B→C→A **явно оставлены на лист «Качество данных»** («ловит лист Качество данных» — дословно).
- `Качества в действиях.Оценка`: `Valid_If: OR(AND(Релевантность="Релевантно", 0<=X<=4), AND(Релевантность="Не релевантно", ISBLANK(X)))` — «жёсткий инвариант — N/A ≠ 0».
- Уникальность пары Действие+Качество: `COUNT(SELECT(...)) = 0` — на уровне AppSheet это тоже должно быть жёсткой блокировкой.
- `Качества в действиях.ID действия`: `IsPartOf = ИСТИНА` — делает таблицу inline-подтаблицей действия («одно действие → список качеств»), это прямое отражение UX-паттерна «одна карточка действия — несколько качеств».
- `Циклы развития.Цели` / `.Качества в фокусе`: тип `EnumList`, `Base type: Ref` — то есть даже в целевой AppSheet-версии это остаётся многозначным полем, а не отдельной junction-таблицей (см. §3.5).

**Раздел B (VC-альтернатива):** даёт AppSheet-нативные выражения для той же статистики, что уже посчитана в Sheets. Здесь есть операционная деталь, которой нет в самом Excel: явная рекомендация **считать 30-дневные окна только для качеств со статусом «Текущий фокус»** — «иначе дорого при росте базы» (масштабируемость).

**Раздел C (что скрыть при переходе):** явно перечисляет lookup-колонки-имена и «служ.: …» как то, что нужно убрать/скрыть — прямое подтверждение классификации «технический артефакт vs. реальные данные», использованной в разделах 3.1–3.6 выше.

**Раздел D (P0 go/no-go, 7 пунктов):** формальный acceptance-чеклист. ## 5. Аналитика — три read-model отчёта

Лист не хранит собственных данных — целиком read-model поверх остальных листов. Три независимых блока:

### 5.1 «Текущий фокус» (строки 3–19, до 15 строк)
Автоматический список: `INDEX(Качества!B, MATCH(ROW()-4, Качества!V, 0))` и аналогично для остальных колонок — то есть **любая** качество со статусом «Текущий фокус» появляется здесь автоматически по своему порядковому номеру (`Качества!V`), без ручного выбора. Колонки: Название, Статус развития, Приоритет, Средняя оценка, Средняя за 30 дней, Тренд, Дата последнего проявления.

### 5.2 «Карточка качества» (строки 22–67)
Управляется вводом в `B23` (DV-список `Качества!$A$2:$A$301`). Три под-блока:
- Полная карточка (VLOOKUP всех полей качества, включая ручной «Текущий уровень»).
- «Последние действия с этим качеством (до 8)» — через `INDEX/MATCH` против `'Качества в действиях'!U` (служебный «обратный ранг»). **Поведенческая деталь:** это последние **по порядку строк ввода** в таблице «Качества в действиях», не по полю «Дата».
- «По контексту — это качество (только релевантные)» — цикл `COUNTIFS`/`AVERAGEIFS` по всем 10 значениям `Справочники!M` (Контекст), т.е. живой pivot «качество × контекст» без сводной таблицы Excel.

### 5.3 «Карточка цели» (строки 69–104)
Управляется вводом в `B70` (DV-список `Цели!$A$2:$A$201`). Три под-блока:
- Полная карточка цели (VLOOKUP, включая ручной Прогресс, %).
- «Последние действия по этой цели (до 8)» — тот же паттерн «обратный ранг по порядку ввода» (`Действия!P`), не по дате.
- «Качества этой цели — сводно, уникальные (до 10)» — на базе `'Качества в действиях'!X` (ранг уникальных пар качество×цель). Для каждого качества: количество проявлений и средняя оценка **в рамках именно этой цели**, плюс сравнение со средней оценкой качества **в целом** (`Качества!L`) с порогом **±0.3**:
```
=IF($C95="","",IF($C95>обычная_средняя+0.3,"↑ выше обычного",
   IF($C95<обычная_средняя-0.3,"↓ ниже обычного","≈ как обычно")))
```
Это единственное место в системе, где качество оценивается **относительно себя же в другом контексте**, а не в абсолютных числах — важный аналитический паттерн для сохранения в SQL (оконная функция / сравнение с агрегатом).

**Общий вывод по разделу 5:** «Аналитика» определяет ровно три готовых read-модели, которые будущий SQL/API-слой обязан уметь воспроизвести: (1) лидерборд текущего фокуса, (2) детальная карточка качества с недавними действиями и разрезом по контексту, (3) детальная карточка цели с недавними действиями и качествами-относительно-нормы. Это прямой прообраз трёх SQL-VIEW или API-эндпоинтов.

## 6. Рекурсия и дерево целей — точный механизм

`Цели!E` (Уровень), `F` (Путь), `O` (Корневая ветка) вычисляются формулой вида `=…VLOOKUP($C2, $A$2:$X$201, N, FALSE())…`, где столбец N — **это же самое** вычисляемое поле (E ищет E, F ищет F, O ищет O). Формально это `E(строка) = E(родительская_строка) + 1`.

Это работает не потому, что Excel исполняет строки по порядку — а потому что **движок Excel строит граф зависимостей и вычисляет ячейки в топологическом порядке**, а не построчно. Поэтому родитель может физически находиться в любой строке относительно потомка (ниже, выше — неважно), и рекурсия всё равно посчитается верно **до тех пор, пока дерево действительно является деревом (без циклов)**.

**Если в данных появляется настоящий цикл** (A ссылается на B, B — на A, или длиннее), у формул `E/F/O` возникает **настоящий Excel circular reference** — потому что взаимная зависимость `E(A)→E(B)→E(A)` реальна, а не просто диагностика. Это не «мягкая» деградация, а полноценная ошибка вычисления, которую Excel обычно помечает предупреждением.

Явный, видимый пользователю флаг `R` («цикл в дереве») **ограничен глубиной 3** (проверяет `C=A`, `P=A`, `Q=A`, то есть себя-родителя, себя-деда, себя-прадеда через служебные колонки P и Q). **Цикл длиной 4 и более не поймает флаг R**, но фактически сломает вычисление E/F/O раньше, чем до него дойдёт очередь любого мониторинга. Это ограничение задокументировано молчаливо (через саму конструкцию P/Q), но не проговорено явно нигде в тексте — важная находка этого аудита.

**Для SQL:** это прямая рекомендация к **рекурсивному CTE** (`WITH RECURSIVE`) с явным отслеживанием пройденного пути (`path`), что даёт **настоящую защиту от циклов любой глубины** — не как «улучшение сверх исходной семантики», а как реализация уже заявленного намерения (Layer 2, §8: «более длинные циклы… требуют либо строгой проверки при изменении Parent, либо периодического integrity-check» — то есть сам дизайн-документ признаёт, что глубина >3 не покрыта, и оставляет решение на будущее).

## 7. Модель валидации — два уровня строгости

Аудит выявил чёткое разделение на два независимых механизма, которые нельзя смешивать при переносе:

**Уровень 1 — настоящая Excel Data Validation (список).** Работает на 11 полях (все перечисленные Enum-колонки + 6 полей с DV-ссылкой на ID других листов). Для однополamerican-доменных ограничений (например, «Оценка должна быть 0/1/2/3/4») это реальное ограничение ввода.

**Уровень 2 — реактивные флаги + лист «Качество данных».** Все межколоночные и межстрочные инварианты (Релевантность↔Оценка, уникальность пары, циклы в дереве, дубли ID) реализованы **только так**: значение можно сохранить в некорректном состоянии, а формула лишь подсвечивает это постфактум. Сам лист прямо называет это advisory («не приказ»).

Это не недосмотр — это **техническое ограничение формул Google Sheets/Excel** (нет триггеров без Apps Script/VBA, а книга сознательно их не использует — Инструкция, п.9: только `VLOOKUP/INDEX/MATCH/COUNTIFS/AVERAGEIFS/MAXIFS/MINIFS`). Design-intent документ (Layer 2) **прямо хочет**, чтобы часть из них была P0-блокировкой (см. §8) — то есть при переносе в SQL часть флагов уровня 2 должна стать **настоящими constraint'ами** (`UNIQUE`, `CHECK`), а не проверочными VIEW.

## 10. Открытые вопросы для владельца системы (до начала проектирования SQL)

1. **Поле «Примечание» у Цели** — есть в design intent, нет в Excel. Добавить в SQL-модель или намеренно опущено?
2. **Порядок «последних N» на карточках качества/цели** («Аналитика», §5.2–5.3) сейчас — по порядку ввода строки, не по дате. Сохранить эту семантику в SQL (`ORDER BY id`/`created_at`) или сознательно перейти на `ORDER BY date DESC`? Это разные результаты, если данные вносятся не строго хронологически.
3. **Циклы ↔ Цели/Качества** — оставить как delimited-текст/массив (ближе к текущей ёмкости и намерению «не спешить») или сразу нормализовать в junction-таблицы? Design intent прямо связывает это решение с «реальным UX-тестом», которого, судя по объёму данных, ещё не было.
4. **Список «Группа качества»** заполнен на 9 из 29 зарезервированных строк, «Приоритет развития» и подобные — тоже открытые списки с явным «можно дополнять». В SQL это аргумент за таблицы-справочники с CRUD, а не `ENUM TYPE` — подтвердить, что это устраивает.
5. **ID генерируются вручную** (`Ц-0001`, `К-0001`, человекочитаемый префикс + номер), а не `UNIQUEID()`, как рекомендует Layer 2 для AppSheet-слоя. Сохранить человекочитаемые ID как первичный ключ (или как отдельное «отображаемое» поле поверх суррогатного `UUID`/`serial`) — тоже решение, которое лучше зафиксировать явно, а не выбрать по умолчанию.

## 11. Что этот документ намеренно НЕ делает

По методологии, зафиксированной в «Финал_Док_Джипити»: этот документ — **исключительно поведенческая спецификация**. Здесь нет ни одной строки SQL DDL, ни выбора между `VIEW`/`materialized view`/физическим полем для каждой формульной колонки — это следующий, отдельный шаг («Excel field → SQL field/view/computation → semantic equivalence», который должен строиться **на основе** этого документа, а не параллельно с ним). Everywhere выше, где дана пометка «→ в SQL: …», это фиксация **природы** поля (технический артефакт vs. реальные данные vs. поведение, которое нужно сознательно решить), а не готовое проектное решение.
