# API CONTRACT — соглашения, которых нет в OpenAPI

Проект строится под **несколько клиентов на одном API** (веб сейчас, мобильное
приложение в Фазе 3, десктоп в Фазе 4). Поэтому контракт — часть архитектуры, а не
документация к ней.

## Как читать этот документ

**Поля и типы смотри в `/docs`** (`/openapi.json`) — он генерируется из кода и не врёт.
Здесь только то, что сгенерировать невозможно: смысл, охват, границы, обещания.

Дублировать сюда список эндпоинтов **нельзя**: рукописная копия разойдётся с кодом на
первом же изменении, и ей будут верить.

---

## 1. Ловушка охвата: одинаковые данные, разный смысл

Самое опасное место в API. Поле `recent_scores` — массив чисел для спарклайна — есть в
трёх ответах, выглядит **одинаково** и означает **разное**:

| Где | Охват |
|---|---|
| `GET /v1/analytics/current-focus` → `recent_scores` | **Глобальный** — вся история качества |
| `GET /v1/qualities` → `recent_scores` | **Глобальный** |
| `GET /v1/goals/{id}/overview` → `qualities[].recent_scores` | **Только внутри этой цели** |
| `GET /v1/goals/{id}/overview` → `subtree.qualities[].recent_scores` | **Цель + все подцели** |

Клиент, перепутавший их, нарисует правдоподобный, но неверный график — и не узнает об
этом: ошибки не будет, просто цифры не те. **Проверяй охват по эндпоинту, не по имени
поля.** Различие закреплено тестом `test_score_series_scope_global_vs_inside_a_goal`.

Порядок во всех случаях — **новые первыми**; клиент разворачивает ряд, чтобы линия
читалась слева направо как течение времени.

## 2. Ошибки

Все ошибки бизнес-логики приходят одинаково:

```json
{ "detail": { "code": "GOAL_NOT_FOUND", "message": "Цель не найдена" } }
```

**`code` — часть контракта, `message` — нет.** Клиент ветвится по `code` и показывает
свой перевод; `message` может измениться в любой момент и существует для отладки.

Коды, на которые клиенты реагируют осмысленно:

| Код | Когда | Что делать клиенту |
|---|---|---|
| `ONE_ACTIVE_CYCLE_ALREADY_EXISTS` | второй активный сезон | показать ссылку на существующий, а не текст ошибки |
| `QUALITY_ALREADY_ADOPTED` | качество уже принято | не ошибка для пользователя, тихо перейти к нему |
| `QUALITY_NOT_FOUND` | нет **принятого** качества с таким id | может значить «есть в каталоге, но не принято» — см. §4 |
| `NOTHING_TO_UPDATE` | пустой PATCH | почти всегда баг клиента, не показывать пользователю |
| `GOAL_NOT_FOUND`, `CYCLE_NOT_FOUND`, `REFLECTION_NOT_FOUND` | нет объекта | обычный «не найдено» |

Валидация (422) приходит в формате FastAPI и в этот контракт не входит.

## 3. Авторизация

Только Google Sign-In. Клиент шлёт Google ID-token в `POST /v1/auth/google`, получает
**свою** пару токенов:

- **access** — короткий (30 мин), в заголовке `Authorization: Bearer`
- **refresh** — долгий (60 дней), **ротируется при каждом обновлении**

Ротация означает: старый refresh перестаёт работать сразу. Повторное использование
уже потраченного refresh считается компрометацией и **отзывает всю сессию** — так
кража токена не даёт долговременного доступа.

Практическое следствие для клиента: обновление токена должно быть **одно на процесс**.
Два параллельных обновления → одно выигрывает, второе получает отзыв сессии. Веб-клиент
решает это общим промисом (`refreshPromise` в `api/client.js`) — мобильному понадобится
свой эквивалент.

## 4. Два пространства идентификаторов

`catalog_quality_id` (качество в общем каталоге, одинаково у всех) и `id` принятого
качества (`user_qualities`, своё у каждого) — **разные идентификаторы**.

`GET /v1/qualities/{id}` принимает **любой из двух**: для человека это одна и та же
«карточка качества». Сначала пробуется как принятое; если приходит `QUALITY_NOT_FOUND`,
клиент ищет id в каталоге.

Причина: «принятое качество» — не пользовательское понятие. Каталог у всех один,
личное состояние ровно одно — в фокусе качество или нет. Строка `user_qualities`
создаётся молча при добавлении в фокус.

---

## 5. PATCH — частичный

PATCH обновляет **только присланные поля**. Не присланное не трогается.

Это не самоочевидно и однажды уже стоило бага: раньше `UPDATE` писал все колонки, и
запрос «сменить фокус» молча сбрасывал приоритет качества на значение по умолчанию.
Тихая порча данных. Закреплено тестом
`test_patch_quality_accepts_a_single_field_and_leaves_the_rest_alone`.

Пустой PATCH — ошибка `NOTHING_TO_UPDATE`, а не «успешно ничего не изменили».

---

## 6. Пагинация — курсорная

`GET /v1/actions` листается курсором, не смещением:

```
?limit=20&before_occurred_at=2026-08-01&before_created_at=2026-08-01T10:00:00Z
```

Курсор составной, потому что `occurred_at` — дата без времени: у нескольких действий за
один день порядок разрешается по `created_at`. Смещение (`offset`) здесь дало бы
пропуски и повторы при вставке новых записей между запросами.

`limit` жёстко ограничен сотней на стороне сервера.

---

## 7. Изоляция данных — на уровне БД

Разделение между пользователями обеспечивает **Row-Level Security PostgreSQL**, а не
условия в запросах. `get_conn(user_id)` выставляет сессионную переменную, которую
читают политики RLS.

Для клиента это значит: сервер физически не может отдать чужие данные, даже при ошибке
в SQL. Для разработчика бэкенда: **любой запрос в обход `get_conn` — дыра**. На это
есть 13 атакующих тестов (`test_security_gate.py`).

Единственное исключение — глобальные справочники (`catalog_qualities`, `ideals`,
`option_lists`): они одинаковы для всех и читаются через `get_conn()` без user_id.

## 8. Уровни стабильности

| Группа | Статус | Чего ждать |
|---|---|---|
| `auth/*`, `goals`, `actions`, `qualities`, `cycles`, `reflections` (CRUD) | **стабильно** | ломающих изменений не планируется |
| `reference/*`, `catalog/*` | **стабильно** | справочники, растут только содержимым |
| `*/overview`, `analytics/*` | **развивается** | сводные ответы; в Фазе 2 добавятся поля |

«Развивается» означает: поля будут **добавляться**, существующие — нет. Клиент,
игнорирующий незнакомые поля, не сломается.

---

## 9. Версионирование

Префикс `/v1` уже есть. `/v2` заводится **только** при ломающем изменении:

- удаление или переименование поля, которое клиенты читают
- изменение типа или смысла существующего поля
- изменение формата ошибок
- смена семантики охвата (см. §1) без переименования поля

Добавление нового поля, нового эндпоинта, нового кода ошибки — **не ломающее**.

При появлении второго клиента (Фаза 3) это перестаёт быть теорией: сломанный контракт
станет виден не сразу, а через магазин приложений, с задержкой в дни.

## 10. Единственный эндпоинт без схемы ответа

`GET /v1/me/export` — **сознательно** без `response_model`.

Схема фильтрует поля, а здесь это противоречит смыслу: выгрузка по GDPR должна включать
**всё**, в том числе колонки, добавленные после написания схемы. Со схемой новая колонка
молча не попала бы в экспорт, то есть право на выгрузку нарушалось бы тихо.

Это решение, а не недоделка. Отмечено и в самом коде, чтобы никто не «починил».

Все остальные операции типизированы (38 из 46; ещё 7 -- это DELETE со статусом 204,
которым схема не нужна по определению); `/docs` полон и достоверен.
